## #3 — 브러시 도구 모음: 크기 조절 UX + 입력창 잘림

### 코드 현황

- 브러시 크기 조절 수단은 현재 **두 가지**: (1) 툴바의 `QSpinBox`(`app/tabs/labeling_tab.py`
  `_build_toolbar()` 221~227행, `range(1,200)`, `setFixedWidth(60)`), (2) 키보드 단축키
  `[`/`-`(−5), `]`/`+`/`=`(+5) (`app/widgets/annotation_canvas.py` `keyPressEvent()` 547~550행).
  더블클릭·우클릭 방식은 **현재 없음**.
- **우클릭은 이미 전역적으로 패닝(pan)에 배정되어 있다** — `mousePressEvent()` 581행:
  `if btn == Qt.MouseButton.RightButton or (...): self._pan_active = True`. 도구 종류와
  무관하게 우클릭 = 패닝이므로, 사용자가 요청한 "우클릭으로 브러시 크기 조절"은 **기존 동작과
  정면으로 충돌**한다. Photoshop류(Alt+우클릭 드래그) 같은 수정자 키 조합 없이는 그대로 쓸 수
  없다.
  - 대안: `Alt+우클릭 드래그`(수평 이동량 → 브러시 크기) 같은 modifier 조합 — 정확한 조합은
    플랫폼 관례가 갈리므로(포토샵/GIMP/Krita가 서로 다름) 확정하지 않고 사용자 확인으로 넘긴다.
- **더블클릭은 브러시/지우개 도구에서 현재 미사용** — `mouseDoubleClickEvent()`(649행)는
  `TOOL_POLYGON`에서 폴리곤 닫기에만 반응, 브러시 계열 도구에서는 아무 동작이 없어 **충돌 없이
  새로 배정 가능**. 다만 더블클릭 시 정확히 무엇을 할지(예: 캔버스에 작은 크기조절 팝업/슬라이더
  띄우기? 클릭 위치 기준 드래그로 조절? 프리셋 크기 순환?)는 코드에 힌트가 없어 UX 설계가
  필요 — 디자인 에이전트 목업 권장.
- **입력창 잘림 버그 — 원인 특정됨**: `main.py`(118~123행) 전역 스타일시트가 `QSpinBox`에
  `padding: 4px 6px`를 적용하는데, 브러시 크기 스핀박스는 `setFixedWidth(60)`(range 1~200,
  즉 최대 3자리)으로 폭이 고정돼 있다. 60px에서 좌우 padding(12px 상당)과 Qt 기본 업/다운
  화살표 폭(스타일에 따라 16~20px)을 빼면 숫자 표시 영역이 30px 안팎으로 좁아져, 3자리 값
  (100~200)에서 실제로 잘려 보일 가능성이 높다. 폭을 넉넉히(예: 76~80px) 늘리거나 padding을
  줄이면 해결되는 **국소적·저리스크 수정**.

### 제안 스코프

- **(a) 잘림 버그**: `_spin_brush.setFixedWidth(60)` → 더 넉넉한 값으로 조정. 목업 불필요,
  즉시 구현 가능(라운드1급 저리스크). 홀리스틱 재검토가 같은 툴바 영역(아이콘)을 이미
  1단계에서 건드렸지만 스핀박스 폭은 손대지 않았으므로 충돌 없음.
- **(b) 더블클릭 대체 조절**: 충돌 없음, 구현은 가능하나 **정확한 인터랙션(더블클릭 시 동작)을
  먼저 확정**해야 함 — 목업 필요.
- **(c) 우클릭 대체 조절**: 기존 패닝과 충돌 — modifier 조합 여부 포함 **사용자 확인 필요**.
  확인 결과에 따라 (b)와 함께 한 라운드로 묶거나, 우클릭 방식은 기각하고 더블클릭만 진행할 수도
  있음.

## #4 — 이미지명 복사 기능 + 오토라벨링 patch training 확인

### 코드 현황

- **복사 버튼 패턴은 이미 프로젝트에 존재**: `app/widgets/settings_dialog.py` 277~308행 —
  `svg_icon("clipboard")` 아이콘의 `QPushButton`(고정폭 36px) + 클릭 시
  `QApplication.clipboard().setText(path_str)` + 버튼 텍스트를 일시적으로 "✓"로 바꿔 피드백,
  타이머 없이 "다이얼로그 재열람 시 자연스럽게 리셋" 방식. `app/resources/icons/clipboard.svg`
  아이콘 리소스도 이미 존재 — **그대로 재사용 가능**, 신규 아이콘/의존성 불필요.
- **추론 탭**: `app/tabs/inference_tab.py`에 이미 `_lbl_filename`(163~165행, 선택된 이미지
  파일명 표시)이 있고 `_on_image_selected()`류 핸들러(244~245행)에서 `path.name`으로 갱신됨.
  이 라벨 옆에 복사 버튼만 추가하면 됨 — **저리스크, 기존 UI 요소에 곁들이기**.
- **라벨링 탭**: 현재 **파일명을 상시 표시하는 UI 요소가 없다**(이미지 브라우저 목록의 선택
  하이라이트로만 간접 확인 가능). 채널 토글 스트립(`_build_channel_strip()`, 20px 높이 고정
  띠, 176행에 `lay.addStretch()`로 여유 공간 있음)에 파일명 라벨 + 복사 버튼을 새로 추가하는
  것이 가장 자연스러운 위치로 판단 — **신규 UI 요소 추가**라 추론 탭보다는 약간 더 손이 감
  (그래도 저리스크, 기존 스트립 레이아웃에 위젯 하나 추가하는 수준).
- **오토라벨링 기본 설정이 patch training인지 — 확인 결과**:
  - 학습 탭(`app/widgets/config_form.py` 41~45행) 샘플링 모드 기본값은 **`random_crop`
    (패치 학습)** — 콤보박스 index 0, `setCurrentIndex(0)`으로 명시적 기본 선택. 즉 학습
    기본값 자체는 patch 방식이 맞다.
  - 그러나 **오토라벨링(`app/core/auto_labeler.py` `_infer_to_annotations()`)은 patch/타일링
    추론을 하지 않는다** — 이미지 전체를 `pil_img.resize(infer_size, Image.BILINEAR)`로
    체크포인트의 `image_w`/`image_h`(즉 학습 시 패치 크기, 보통 512×512급)로 **다운스케일해서
    통째로 1회 추론**한다(패치를 슬라이딩해서 이어붙이는 로직 없음).
  - 즉 답은 **"아니오"** — 모델을 random_crop(패치) 방식으로 학습했더라도, 오토라벨링 시점에는
    원본 대형 이미지 전체를 작은 크기로 뭉개서 넣는 단일 추론 방식이다. 학습 때 모델이 본
    입력(원본 해상도의 국소 패치)과 추론 때 넣는 입력(전체 이미지의 저해상도 축소본)의 분포가
    달라 **정확도 저하 가능성이 있는 기존 갭**으로 보인다. 다만 이는 **이번 GitHub 이슈가
    요청한 범위가 아니고**(사용자는 "확인"만 요청), 고치려면 오토라벨러에 슬라이딩 윈도우 타일
    추론을 새로 구현해야 하는 별개의 상당한 작업이라 이번 스펙에서는 **사실관계 확인으로 종결**
    — 별도 개선이 필요하다고 판단되면 이후 별도 요청/라운드로 다룰 것을 권장.

### 제안 스코프

- 라벨링 탭 + 추론 탭에 `settings_dialog.py`와 동일한 클립보드 복사 버튼 패턴 적용. 난이도 하,
  목업 불필요(기존 승인된 패턴 그대로 복제).
- patch training 확인 질문은 **구현 불필요** — 위 사실관계 기록으로 답변 완료.

## #5 — 모델 탭을 독립 탭에서 학습 탭 "+" 모달로 전환

### 코드 현황 (영향 범위)

- 현재 `app/main_window.py` 31~40행: `MainWindow`가 `self._model_tab = ModelTab()`을
  생성해 `QTabWidget`에 4번째 탭으로 addTab. `ModelTab`(`app/tabs/model_tab.py`)은 일반
  `QWidget`(코드 에디터 + 검증/로드 버튼)이라 탭 인덱스나 부모가 `QTabWidget`이라는 전제에
  의존하는 코드는 없음(자체 완결적 위젯) — **다이얼로그로 옮기는 것 자체는 위젯 구조상 무리
  없음**.
- **핵심 리스크는 상태 공유**: `win._model_tab.loaded_model`을 **3개 탭이 교차 참조**한다 —
  `training_tab.py`(734~738행, 큐에 넣을 모델 소스가 `"loaded"`일 때), `labeling_tab.py`
  (487~491행, 오토라벨링 시 로드된 커스텀 모델 사용 — 단, 모델 미로드 시 프리셋으로 자체
  인스턴스화하는 폴백이 있어 완전히 막히지는 않음), `inference_tab.py`(430~434행, 체크포인트의
  `model_source`가 `"loaded"`일 때 아키텍처 재구성용). 세 곳 모두 `self.window()`로
  `MainWindow`를 얻은 뒤 `_model_tab` 속성에 접근하는 동일 패턴.
  - **따라서 구조 변경 시 반드시 지켜야 할 제약**: `MainWindow`가 `ModelTab` **인스턴스를
    하나만 계속 들고 있어야** 한다(현재처럼 `self._model_tab = ModelTab()`을 그대로 유지).
    "+" 버튼을 누를 때마다 새 `ModelTab()`을 만들면 로드된 모델 상태가 매번 초기화돼 위 3곳이
    깨진다 — **표시 컨테이너만 QDialog로 바꾸고, 위젯 인스턴스 자체는 재사용**하는 방식이어야
    함.
  - 구현 방식 후보(결정 아님, 참고용): 이미 프로젝트에 `model_preset_dialog.py` 같은 QDialog
    관례가 있으므로 신규 라이브러리/패턴 도입은 아님. 다만 **매번 위젯을 새 QDialog로
    reparent하는 방식은 위험**(Qt는 부모-자식 소유권 모델이라, 다이얼로그가 닫히고 GC될 때
    자식 위젯까지 함께 삭제될 수 있어 다음 클릭 시 삭제된 C++ 객체 접근으로 크래시 가능) —
    **다이얼로그를 최초 1회만 지연 생성해 재사용**(`show()`/`raise_()`)하는 방식이 더 안전한
    후보로 보인다. 구현 단계에서 검토.
- `main_window.py`에 탭 인덱스 기반 로직(`setCurrentIndex`, 단축키 등)은 없음(grep 확인) —
  탭 개수가 4→3으로 줄어도 부수적으로 깨지는 다른 코드는 발견되지 않음.
- i18n: `tab.model` 키(ko "모델"/en "Model")가 현재 탭 제목으로 쓰임 — 다이얼로그 타이틀로
  재사용하거나 신규 키 추가 필요(사소).

### UX 영향 — 탭 기반 구조와의 정합성

- 현재 4탭(라벨링/학습/추론/모델)은 대등한 워크플로우 단계로 취급되고 있고, `CLAUDE.md`
  디렉토리 구조상으로도 `app/tabs/`에 4개가 나란히 정의돼 있다. 모델 탭만 "학습 탭에 종속된
  팝업"으로 바뀌면 **탭 = 대등한 4대 기능**이라는 기존 UI 문법이 깨진다. 사용자 요청 의도(모델
  설정은 학습 준비 단계에 가깝다는 관점)는 타당하지만, 이는 **프로젝트 전반의 UI 패러다임을
  바꾸는 결정**이라 리더가 사용자에게 먼저 확인해야 한다(과도한 정형화가 아니라, 실제로 라벨링/
  추론 탭이 `_model_tab`을 참조하는 구조상 파급 범위가 실재함).
- 라벨링 탭 오토라벨링 진입 동선 변화: 지금은 "모델 탭에서 로드 → 라벨링 탭에서 사용" 흐름이
  자연스러운데, 모델 탭 진입점이 "학습 탭의 +"뿐이 되면 라벨링 탭 사용자가 커스텀 모델을
  로드하려 할 때 학습 탭까지 갔다 와야 하는 동선이 하나 추가된다(단, 위에서 확인했듯 오토라벨은
  프리셋 폴백이 있어 완전 차단은 아님). 구조 변경을 진행하기로 하면 라벨링 탭에서도 같은 "+"
  진입점을 함께 노출할지 여부를 디자인 단계에서 결정할 필요가 있음.

### 결론

**즉시 결정하지 않고 사용자 확인 대기로 분류** — `docs/decisions-needed.md`에 등록(아래
"사용자 확인 필요" 절 참고). 진행하기로 확정되면 디자인 에이전트의 목업(+" 배치 위치, 다이얼로그
크기/타이틀, 라벨링 탭 보조 진입점 여부)을 먼저 받고 구현.

## #6 — annotation 로딩/깜빡임 (2건: 성능 저하 + flicker, 둘 다 `_invalidate_overlay()` 계열이지만 서로 다른 결함)

리더 지시로 원래 GitHub #6 제목("annotation 로딩 느림")과 겹치는 사용자의 추가 구체 보고를
함께 다룬다. 사용자 표현: **"annotation이 많아지니까 추가하거나 화면이 바뀔 때 로딩 속도가
매우 느려져. 이 부분 최적화가 반드시 필요해."** — 즉 원래 GitHub 이슈 원문("깜빡임")보다
더 구체적이고 심각한 별개 현상(개수에 비례한 지연)이다. 조사 결과 **원인이 다른 두 문제**로
갈린다:

- **#6-A (flicker)**: 원래 GitHub #6 원문이 말한 "깜빡임" — 오버레이가 사라졌다 다시
  나타나는 타이밍 버그. 원인 국소적, 수정 저리스크.
- **#6-B (개수 비례 지연, 사용자가 "반드시 필요"로 명시)**: 어노테이션 개수가 많아질수록
  (a) 추가할 때, (b) 이미지/화면 전환할 때 둘 다 체감 로딩이 느려지는 현상. 원인이 더 구조적
  (매 편집마다 전체를 처음부터 다시 그리는 O(n) 재구축 로직 2곳)이라 수정 난이도·리스크가 더
  높다. **사용자가 "반드시 필요"라 명시했으므로 이번 라운드에서 우선순위를 가장 높게 둔다.**

두 문제 모두 `_invalidate_overlay()`와 그 호출부가 얽혀 있어 같은 절에서 함께 다루되, **수정
방향은 서로 다르다** — A는 "오버레이를 언제 교체하느냐"의 타이밍 문제, B는 "오버레이/목록을
다시 그리는 데 걸리는 시간 자체"가 개수에 비례해 커지는 문제라 A를 고쳐도 B는 그대로 남는다.

### #6-B — 어노테이션 개수 증가 시 로딩 지연 (최우선, 원인 특정됨)

정적 코드 분석으로 **서로 독립적인 O(n) "전체 재구축" 지점 2곳**을 확인했다(n = 현재 이미지의
어노테이션 개수). 편집이든 이미지 전환이든 둘 다 이 2곳을 반드시 거친다:

1. **`app/tabs/labeling_tab.py` `_refresh_ann_list()`(453~484행)** — 어노테이션 목록
   패널(`_ann_list`, `QListWidget`)을 **매번 `clear()` 후 전체를 `QListWidgetItem`으로
   처음부터 다시 생성**한다. 클래스 조회·색상 계산·문자열 포맷팅까지 어노테이션 개수만큼
   반복 — **메인 스레드에서 동기적으로 실행**되므로 개수가 많을수록 UI가 그대로 멈추는 형태로
   체감된다. 호출 시점: 이미지 전환 직후(364행), 그리고 **매 편집마다**(`_on_annotation_saved()`
   372~380행 — `canvas.annotation_saved` 시그널에 연결, 500ms 디바운스된 저장 1회당 1번씩
   호출, 380행). 즉 어노테이션 1개를 추가/수정할 때마다 나머지 n-1개까지 포함한 리스트
   전체를 재구성한다 — 정작 바뀐 건 1개인데 O(n) 작업을 매번 반복하는 전형적 패턴.
2. **`app/widgets/annotation_canvas.py` `_rebuild_overlay()` / `_OverlayWorker.run()`
   (21~76행, 1379~1439행)** — 오버레이 픽스맵(어노테이션 시각화)을 **매번 전체
   어노테이션을 처음부터 다시 그려서** 생성한다. 폴리곤은 `drawPolygon`, `brush_mask`는
   `_draw_mask_on_painter()`(1627~1638행, numpy→QImage 변환은 벡터화돼 있어 픽셀루프는
   아님)를 어노테이션 개수만큼 반복 호출 — 선택된 항목은 추가로 `cv2.dilate` 테두리 계산까지
   더해짐. 백그라운드 `QThread`(`_OverlayWorker`)로 오프로드돼 있어 **메인 스레드를 완전히
   멈추지는 않지만**, 어노테이션 개수에 비례해 워커 실행 시간 자체가 늘어나므로 "새로 그린
   오버레이가 반영되기까지" 걸리는 시간이 길어진다 — 개수가 많을수록 체감 지연 + (위에서 이미
   확인한) flicker 창이 함께 길어짐. 호출 시점은 `_invalidate_overlay()`가 호출되는 모든
   지점(이미지 전환 `load_image()` 333행 포함, 편집마다) — **1개만 바뀌어도 전체 재렌더링**은
   위 1번과 동일한 패턴.
   - 부수 확인: `_resolve_overlap_and_merge()`/`_consolidate_class_region()`
     (1038~1160행)도 브러시 스트로크 완료마다(디바운스 없이 즉시) `self._annotations` 전체를
     최소 2~3회 순회한다(픽셀 독점성 처리, 빈 마스크 제거, 동일 클래스 병합 후보 탐색). 각
     순회 자체는 브러시 bbox 크기로 제한돼 있어 개별 비용은 작지만(R3/R7 이전 최적화가 이미
     20MP 전체 스캔은 막아둠), **"어노테이션 개수만큼 Python 루프를 도는" 구조 자체는 여전히
     O(n)**이라 개수가 매우 많아지면 누적 비용이 커진다 — 브러시 편집 시 지연의 2차 기여
     요인으로 기록(주요 원인은 위 1·2번).

**결론**: 두 지점(라벨링 탭 어노테이션 목록 재구축, 캔버스 오버레이 재구축) 모두 "바뀐 것만
갱신"하지 않고 "매번 전체를 처음부터 다시 만든다"는 같은 설계 패턴이 원인이다. 이는 R1~R6
성능개선 라운드가 다룬 영역(이미지 디코딩 캐시, 검색 디바운스 등)과는 **다른 코드 경로**이며,
R3가 만든 회귀가 아니다(R3는 `_pixmap`/`_display_pixmap` 캐시만 다뤘고 `_overlay`/
`_ann_list` 재구축 로직은 손대지 않음).

**유력 해결 방향(제안, 결정 아님)**:
- `_refresh_ann_list()`: 매번 `clear()` + 전체 재생성 대신, 이전 어노테이션 ID 집합과 새
  집합을 비교해 **추가/삭제된 항목만 add/remove**하고 기존 항목은 그대로 두는 증분 갱신으로
  전환. (단순 병합처럼 ID가 유지되는 편집은 항목 재생성 자체가 필요 없어짐.)
- `_rebuild_overlay()`: 진짜 "바뀐 어노테이션만" 다시 그리려면 어노테이션별 캐시된 서브비트맵을
  합성하는 구조로 바꿔야 하는데, 이는 오버레이 컴포지팅 방식 자체를 바꾸는 **더 큰 리팩터**라
  구현 난이도가 상대적으로 높음. 저리스크 중간 단계로는: (a) 전체 재빌드는 유지하되 디바운스를
  걸어 짧은 시간 내 연속 편집(예: 빠른 연속 브러시 스트로크)에서 중간 상태의 재빌드를
  스킵·병합, (b) 어노테이션 개수가 매우 많을 때(예: 200개+) `overlay_scale`을 더 공격적으로
  낮춰 개별 `_draw_mask_on_painter` 비용을 줄이는 것부터 시작하는 안이 있음 — **구현 단계에서
  비용 대비 효과를 저울질해 확정할 것**.
- 두 항목 모두 **정적 분석만으로 원인은 확정**됐으나, R6 사례(2026-08-19)와 마찬가지로
  현재 `projects/nok/`처럼 소규모 프로젝트로는 개선 폭을 실측하기 어렵다 — **검증 단계에서
  어노테이션 수백 개 규모의 합성 이미지(예: 브러시 마스크 200~500개)로 전/후 벤치마크를
  수행해 실제 개선폭을 정량 확인**하도록 조건을 명시한다(R6 검증 방식과 동일 관례).

#### 난이도·리스크 (#6-B)

중~상. 원인은 확정됐지만 `_rebuild_overlay()`쪽 수정은 오버레이 컴포지팅 구조에 손을 대야 할
가능성이 있어(위 해결방향 참고) 단순 버그 수정보다 리스크가 크다. 목업은 불필요(시각적 변경
아님, 성능 리팩터). `annotation_canvas.py`(1638줄 대형 파일)와 `labeling_tab.py` 양쪽을
같이 건드리므로 **별도 라운드로 분리**하고, 브러시/폴리곤/지우개/선택 각 편집 골든패스 +
대규모 합성 프로젝트 벤치마크로 검증할 것을 권장.

### #6-A — annotation 깜빡임 (제목은 "로딩 느림"이지만 실제는 flicker)

#### 코드 현황 — 원인 특정됨

`app/widgets/annotation_canvas.py`의 `_invalidate_overlay()`(1343~1351행)가 원인이다:

```python
def _invalidate_overlay(self) -> None:
    ...
    self._overlay = None        # ← 즉시 오버레이를 지움 (동기)
    self._overlay_dirty = True
    if self._img_w > 0:
        self._start_overlay_worker()   # ← 재생성은 QThread(_OverlayWorker)로 비동기
```

- 오버레이(어노테이션 시각화 픽스맵)는 백그라운드 `QThread`(`_OverlayWorker`)에서 재생성되고,
  완료되면 `_on_overlay_done()`이 `self._overlay`를 교체한 뒤 `self.update()`를 호출한다.
  **`_overlay = None`으로 지운 시점부터 워커가 끝나 새 오버레이가 반영되기까지의 구간에 발생하는
  모든 `paintEvent`는 오버레이 없이(어노테이션이 안 보이는 채로) 그려진다** —
  `paintEvent()` 508행: `if self._overlay is not None and self._overlay_visible:` 게이트가
  `None`일 때 그리기 자체를 건너뛰기 때문. 이것이 "어노테이션이 순간적으로 사라졌다 다시
  나타나는" 깜빡임의 정확한 메커니즘이다.
- **호출 지점이 매우 광범위**하다(같은 파일에서 15곳 이상): 브러시 스트로크 완료
  (`_finish_brush()` 887행 — 스트로크마다 1회), 폴리곤 완성, 지우개 적용, 선택 변경뿐 아니라
  **이미지 전환**(`load_image()` 333행)에서도 호출된다. 즉 VOC 원문의 "annotation 추가할 때"
  뿐 아니라 이미지를 넘길 때도 동일한 메커니즘으로 발생한다.
- **채널 전환(`set_channel()`, 1492~1499행)은 오버레이를 건드리지 않는다** — 대신
  `_display_pixmap`을 초기화하고, 다음 `paintEvent`가 `_get_display_pixmap()`을 **동기적으로**
  다시 계산한다(`_apply_channel_filter()`가 전체 해상도 QImage↔numpy 왕복 변환, 배경 스레드
  없이 메인 스레드에서 처리). nok급 대형 이미지(5472×3648)에서는 이 동기 계산이 체감 지연을
  유발할 수 있지만, "오버레이가 사라지는" 방식의 flicker는 아니다 — 채널 전환 자체는 오버레이
  flicker의 직접 원인이 아니다. VOC 원문 "채널변경하면서 라벨링하거나"는 **채널 전환 직후 곧바로
  라벨링(브러시 등)해서 `_invalidate_overlay()`가 겹쳐 호출되는 복합 상황**을 가리키는 것으로
  판단된다 — 두 지연(채널 필터 동기 계산 + 오버레이 재생성 비동기 갭)이 겹쳐 체감 flicker가 더
  두드러질 뿐, 근본 원인은 여전히 하나(`_invalidate_overlay()`)다.
- **R3(성능개선, 이미지 캐시)와의 관계**: R3는 `load_image()`의 `_pixmap`/`_display_pixmap`
  캐시(픽셀 디코딩 경로)와 bbox fallback 스캔을 다뤘고, `_invalidate_overlay()`/
  `_OverlayWorker`(오버레이 경로)는 건드리지 않았다 — **R3가 만든 회귀가 아니다.** 오버레이를
  백그라운드 스레드로 비동기 처리하는 구조 자체는 그보다 이전부터 있던 설계로 보인다(대형
  이미지에서 오버레이 재계산이 메인 스레드를 막지 않게 하려는 의도 — 목적은 좋으나 전환 순간의
  "빈 프레임" 처리가 누락된 상태).

#### 유력 해결 방향 (제안, 결정 아님 — 구현 단계에서 확정)

`_invalidate_overlay()`에서 `self._overlay = None`을 즉시 실행하지 않고, **재생성이 완료될
때까지 이전(stale) 오버레이를 계속 그리다가 새 오버레이가 준비되면 그때 교체**하는 방식(흔한
더블 버퍼링 패턴). 최악의 경우 방금 그린 스트로크 1개가 아주 잠깐(워커 처리 시간만큼) 늦게
반영되는 정도이고, "어노테이션이 통째로 사라짐"보다 훨씬 덜 거슬린다. 수정 범위가
`_invalidate_overlay()` 함수 내부로 좁아 국소적·저리스크 — 원인이 명확히 좁혀져 있어
스파이크는 불필요.

#### 제안 스코프 (#6-A)

- 난이도 하~중(원인 국소화 완료, 수정 범위 1개 함수). 목업 불필요(시각적 디자인 변경이 아니라
  타이밍 버그 수정). 검증 시 (1) 연속 브러시 스트로크, (2) 연속 이미지 전환, (3) 채널 전환 직후

  R3와 동일 수준의 검증 필요).

## #7 — OK 처리 시 기존 라벨 삭제 확인 팝업

### 사용자 주장 검증 — 사실로 확인됨

GitHub #7 원문: "라벨이 있는 상태에서 OK 취급하게 하려면 팝업창을 띄워서 없애도 되는지 확인" —
요청 3단계: (1) 라벨(어노테이션)이 있는 이미지를 OK 처리할 때 확인 팝업 표시, (2) 확인하면
기존 라벨을 제거하고 OK 처리, (3) 취소 옵션 제공.

코드 확인 결과 **현재 확인 팝업이 없다는 사용자 주장은 정확**하다:
- `app/tabs/labeling_tab.py` `_on_toggle_ok()`(418~422행)는 조건 없이 바로
  `self._canvas.toggle_ok()`를 호출한다.
- `app/widgets/annotation_canvas.py` `toggle_ok()`(402~407행)는
  `store.set_ok(path, not current, ...)`만 호출 — **어노테이션 리스트(`self._annotations`)는
  전혀 건드리지 않는다.**
- `app/core/annotation_store.py` `set_ok()`(184~201행)도 JSON의 `"ok"` 키만 추가/제거할 뿐
  `"annotations"` 배열은 그대로 둔다. `save()`(108~145행)도 저장 시 기존 `ok` 플래그를
  보존(`ok_flag = get_ok(image_path)`)할 뿐 둘을 상호 배타로 취급하지 않는다.
- 실제 동작: 라벨이 있는 이미지를 OK 처리해도 **라벨은 삭제되지 않고 JSON에 그대로 남는다**
  (데이터 유실은 없음). 다만 `get_label_status()`(158~171행)가 `ok` 플래그를 `annotations`
  존재 여부보다 먼저 검사하므로, 라벨 상태 아이콘·목록에서는 "ok"로만 보이고 그 밑에 라벨이
  남아있다는 사실이 UI상 드러나지 않는다 — 그리고 애초에 "라벨이 있는데 OK로 표시해도 되는지"
  묻는 확인 절차 자체가 없다.

### 제안 스코프

기존에 동일 UI 패턴이 이미 있어 신규 설계 없이 재사용 가능:
- `_on_clear_all()`(`labeling_tab.py` 407~416행)이 "전체 삭제" 시 이미
  `QMessageBox.question(... Yes/No)` 확인을 거쳐 `clear_all_annotations()`를 호출하는
  **동일한 확인→실행 패턴**을 쓰고 있다 — OK 토글에도 그대로 복제 가능.
- `clear_all_annotations()`(`annotation_canvas.py` 386~395행)가 이미 어노테이션 전체 삭제 +
  undo 스택 반영 + 오버레이 무효화 + 저장 예약까지 다 처리하는 **재사용 가능한 기존 메서드**.
- `_on_toggle_ok()`가 이미 "이미지 미선택 시 `_act_ok.setChecked(False)`로 되돌리기"(420행)
  패턴을 쓰고 있어, **취소 시 체크 상태 되돌리기**도 동일하게 복제 가능(체크형 `QAction`은
  클릭 즉시 체크 상태가 바뀐 뒤 `triggered`가 발생하므로, 취소 시 명시적으로 되돌려야 함 —
  기존 코드가 이미 이 패턴을 알고 처리 중).
- 로직: OK를 **켜는** 순간(끄는 경우는 그대로 무확인)이면서 `self._canvas._annotations`가
  비어있지 않으면 확인 팝업 → Yes면 `clear_all_annotations()` 호출 후 `toggle_ok()`, No/취소면
  `_act_ok.setChecked(False)`로 되돌리고 아무 것도 하지 않음.
- i18n: 새 키 2개 필요(`labeling.ok_clear_title`/`labeling.ok_clear_msg` 등, ko/en 둘 다 —
  기존 `labeling.clear_title`/`labeling.clear_msg` 옆에 나란히 추가하는 수준).

### 난이도·리스크

하. 새 아키텍처·다이얼로그 클래스·목업 전부 불필요 — 같은 파일 안에 이미 있는 확인 패턴
2개(`_on_clear_all`의 QMessageBox 확인, `_on_toggle_ok`의 체크상태 되돌리기)를 조합하는
수준. 리스크는 낮으나 **"OK를 껐다가 다시 켤 때"·"어노테이션 없는 이미지"·"이미 OK인
이미지의 라벨 추가 후 재-OK 시도" 등 경계 케이스를 구현 시 빠짐없이 확인할 것.
