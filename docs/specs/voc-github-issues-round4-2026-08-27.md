## GitHub #17 — 이미지 목록 다중선택 → Ctrl+C 파일명 복사

### 문제 정의
이미지 브라우저(`app/widgets/image_browser.py`)의 `_tree`(`QTreeWidget`)는 이미
`ExtendedSelection`(Ctrl/Shift 다중선택 가능, GitHub #8에서 확인됨)이지만, 키보드
단축키 핸들러가 전혀 없다(`keyPressEvent`/`eventFilter` 미구현 확인). Ctrl+C를 눌러도
아무 반응이 없다.

### 스코프
- **대상 파일**: `app/widgets/image_browser.py` 1곳만 수정.
- **구현 방식 제안**: `_tree`는 `QTreeWidget` 인스턴스를 직접 생성해 쓰는 구조라
  (`ImageBrowser.__init__`→`_build_ui()`에서 `self._tree = QTreeWidget()`), 서브클래싱
  대신 `self._tree.installEventFilter(self)` + `ImageBrowser.eventFilter()`에서
  `QEvent.Type.KeyPress` + `Qt.Key.Key_C` + `ControlModifier` 조합을 가로채는 방식이
  가장 적은 변경으로 끝난다(새 클래스 불필요).
- **복사 대상**: "파일명들"이라는 원문에 따라 **파일명만**(디렉토리 경로 제외).
  **확장자 포함**으로 제안 — `_on_delete()`의 확인 다이얼로그가 이미 `p.name`(확장자
  포함, 예: `img001.jpg`)으로 미리보기를 표시하는 기존 관례와 일치시킴. 별도 결정 불필요
  (사소한 선택, 위 관례 재사용이면 충분).
- **정렬 순서**: `_tree.selectedItems()`가 반환하는 순서 그대로 사용(일반적으로 트리
  표시(문서) 순서와 일치) — 별도 재정렬 로직 불필요.
- **구분자**: 줄바꿈(`\n`)으로 join 후 `QApplication.clipboard().setText()`.
- **적용 조건**: 선택된 항목이 0개면 아무 동작 안 함(빈 문자열 복사 방지).

### 참고 — 유사 패턴 기존 코드
`app/widgets/settings_dialog.py`에 이미 `QApplication.clipboard().setText()` 클립보드
복사 패턴이 있고(GitHub #4에서 재사용됨), 이번에도 그대로 재사용 가능 — 신규 유틸 불필요.

### 결정 필요 사항
없음 — 바로 구현 가능.

### 검증 골든 패스
1. 이미지 브라우저에서 Ctrl/Shift로 2개 이상 선택 → Ctrl+C → 메모장 등에 붙여넣기 →
   줄바꿈으로 구분된 파일명(확장자 포함) 목록 확인.
2. 단일 선택 상태에서 Ctrl+C → 파일명 1개만 복사되는지 확인.
3. 선택 없는 상태(포커스만 있고 아무것도 선택 안 됨)에서 Ctrl+C → 크래시/빈 복사 없는지 확인.
4. 검색/정렬 필터가 걸린 상태에서도 정상 동작하는지 확인(필터된 `_paths` 기준으로
   보이는 항목만 복사 대상이 되는지).
5. 다른 위젯(검색창 `QLineEdit` 등)에 포커스가 있을 때 Ctrl+C를 눌러도 이미지 브라우저의
   복사 로직이 오동작하지 않는지(이벤트 필터가 `_tree`에만 걸려 있어야 함) 확인.

## GitHub #16 — 내보내기 실패 (PermissionError, WinError 32)

### 배경 재확인
사용자가 첨부한 실제 크래시 로그는 `self._pairs`를 참조하는 **구버전 코드** 기준이다
(오늘 커밋 `7dabdb5`로 `export_dialog.py`가 `self._pairs`→`self._image_paths`로 이미
리팩터링됨, `docs/agents/implementation-log.md` 참고 — 이건 MemoryError 문제 수정이었고
이번 이슈와는 무관). 하지만 **PermissionError 자체(`shutil.copy2`가 소스 이미지 파일을
읽지 못함)는 그 리팩터링과 별개의 버그이며, 현재 HEAD 코드에도 그대로 남아 있다.**

### 조사 결과

#### 재현 여부
**로컬 재현 실패** — 이 세션 환경에서는 실제 OS 레벨 파일 잠금을 인위적으로 만들 수
없어 코드 감사(정적 분석)로만 원인을 좁혔다. 사용자 환경 자체를 재현할 방법(백신 종류,
OneDrive 등 클라우드 동기화 여부, Explorer 미리보기 창 열림 여부)을 알 수 없어 실측
재현은 이번 라운드 범위 밖.

#### 원인 후보 — 순위별 정리

**1순위 (외부 프로세스, 가능성 높음)** — Windows 에러 메시지 자체("다른 프로세스가
파일을 사용 중")가 이 진단을 직접 뒷받침한다:
- Windows 탐색기 미리보기 창/썸네일 캐시 생성이 이미지 파일을 순간적으로 잠금
- 백신 실시간 검사가 새로 접근된 이미지 파일을 스캔하는 동안 잠금
- OneDrive/구글드라이브 등 클라우드 동기화 클라이언트가 `images_dir`이 동기화 폴더
  안에 있을 경우 업로드/온디맨드 다운로드 중 파일을 잠금
- 사용자 환경 경로가 `d:\SW python\46-corrisioin-seg-tool`로 원래 리포지토리와 다른
  폴더명 — 이 프로젝트를 복제/포크해 실사용 배포 중인 것으로 보이며, 그 환경의 폴더
  위치(동기화 폴더 여부 등)를 알 수 없다는 점도 이 가설을 뒷받침(정보 부족일 뿐 반증은
  아님).

**2순위 (내부, 가능성 낮음)** — 이 앱 자체가 파일 핸들을 쥐고 있을 가능성을 코드
감사로 확인:
- `app/widgets/export_dialog.py`의 `_image_size()`는 이미 `with Image.open(path) as im:`
  으로 안전하게 닫힘. `_export_json/_export_yolo/_export_coco` 전부 `load_annotations()`
  (JSON 파일, 이미지 아님)만 열고 이미지 자체는 `shutil.copy2`가 읽기 전용으로 여는 것이
  전부 — export_dialog.py 자체에는 이미지 파일을 열어둔 채 방치하는 코드가 없음.
- `app/core/dataset.py`의 `_load_cached()`(학습 데이터로더 LRU 캐시)가
  `Image.open(img_path).convert("RGB")` 결과 객체를 캐시에 **장기 보관**하지만, PIL의
  `Image.load()`(= `.convert()`가 내부적으로 호출)는 `_exclusive_fp=True`(파일 경로로
  직접 열었을 때)인 경우 픽셀 데이터를 다 읽은 직후 OS 파일 핸들을 즉시 닫는다 — 캐시에
  남는 것은 디코딩된 픽셀 배열(메모리)이지 열린 파일 핸들이 아님. **이 캐시는 OS 레벨
  파일 잠금의 원인이 아닌 것으로 판단.**
- `app/core/auto_labeler.py:70` `img = Image.open(str(img_path))` — `.convert()`/`.load()`
  를 호출하지 않고 `.width`/`.height`(헤더 정보, lazy 로드라 파일을 다 읽지 않음)만 접근함.
  이 경우 OS 파일 핸들이 **다음 루프 반복까지** 열려 있을 수 있다(CPython 참조 카운트로
  다음 `img = Image.open(...)` 대입 시점에 이전 객체가 GC돼 닫힘). 다만 Windows에서
  CPython 내장 `open()`/PIL이 기본으로 사용하는 공유 모드는 다른 프로세스의 읽기/쓰기를
  막지 않는 "deny-none"이 기본값이라, 이 앱 자신의 핸들이 **자기 자신의 `shutil.copy2`
  호출**을 막을 개연성은 낮다(같은 프로세스 내 협조적 접근이라면 더더욱). 다만 자동
  라벨링(전체 프로젝트 순회, 백그라운드 `QThread`)이 실행되는 도중 사용자가 **정확히 같은
  이미지**를 대상으로 내보내기를 동시에 실행하는 경쟁 상황이면 이론상 완전히 배제할 수는
  없음 — 근본 원인일 가능성은 낮지만(외부 프로세스 가설보다 약함), 위생 차원에서 고치는
  것을 권장.
- `app/widgets/annotation_canvas.py:330` `self._pixmap = QPixmap(str(path))` — Qt의
  이미지 로더는 디코딩 즉시 내부적으로 파일을 닫는 구조라(Qt가 직접 여는 `QFile` 기반),
  라벨링 탭에 이미지가 표시돼 있다고 해서 파일 핸들이 계속 열려있지는 않을 것으로 판단.
- `app/widgets/export_dialog.py`의 `ExportDialog`는 `main_window.py`에서
  `dlg.exec()`(모달)로 열린다 — 메인 스레드 위젯 조작은 막히지만, 학습/추론/자동라벨링의
  백그라운드 `QThread` 워커는 모달 다이얼로그와 무관하게 계속 실행될 수 있다. 즉 "내보내기
  중 다른 작업이 그 이미지를 동시에 건드릴 수 없다"는 보장이 앱 안에 없다 — 사용자가
  학습/추론/자동라벨링을 백그라운드에서 돌리는 도중 내보내기를 실행했을 가능성도 배제 못함
  (사용자에게 재현 조건으로 확인 필요, 아래 질문 참고).

**결론**: 내부 코드에 "명백한 상시 파일 잠금 버그"는 발견되지 않았다. 가장 유력한
원인은 앱 외부 요인(백신/탐색기/동기화 클라이언트)이며, 내부적으로는 `auto_labeler.py`
비-`with` 패턴이 이론적 가능성으로만 남는다.

### 제안하는 수정

**주 수정 (원인 불명이어도 항상 유효한 방어책)** — `export_dialog.py`의
`shutil.copy2(img_path, img_out / img_path.name)` 호출 3곳(`_export_json`,
`_export_yolo`, `_export_coco`)을 짧은 retry+backoff 헬퍼로 감싼다. 외부 프로세스의
파일 잠금은 대개 수십~수백 ms 안에 해제되는 일시적 현상이므로, 예: 3회 재시도
(즉시 실패 시 100ms → 300ms → 900ms 대기 후 재시도), `PermissionError`/`OSError`만
잡고 마지막 시도도 실패하면 그대로 raise(기존 `run()`의 `except Exception` →
`error` 시그널 → `QMessageBox.critical` 경로는 그대로 유지, 예외를 삼키지 않음 —
CLAUDE.md "core 모듈은 예외를 그대로 raise" 원칙 준수). 3개 함수가 동일 패턴을
반복하므로 헬퍼 함수 하나(`_copy_with_retry(src, dst)`)로 통합해 중복 제거.

**보조 수정 (위생, 낮은 우선순위)** — `app/core/auto_labeler.py:70`의
`img = Image.open(str(img_path))`를 `with Image.open(str(img_path)) as img:`로 감싸
루프 반복 사이 파일 핸들이 열려 있는 구간 자체를 제거. 근본 원인일 개연성은 낮지만
고치는 비용이 1줄 수준이라 겸사겸사 처리 권장.

**하지 않는 것**: `dataset.py`의 LRU 캐시는 설계 의도된 성능 최적화이고 파일 핸들을
쥐고 있지 않음이 확인됐으므로 손대지 않음.

### 사용자에게 확인하면 좋을 질문 (선택, 결정 대기 등록 대상 아님 — 구현 진행을
막을 필요는 없음)
1. 내보내기 실패 당시 프로젝트의 `images/` 폴더가 OneDrive 등 클라우드 동기화 폴더

   있었는지?
3. 내보내기 실행과 동시에 학습/추론/자동 라벨링을 백그라운드에서 돌리고 있었는지?
4. 실패가 항상 재현되는지, 아니면 가끔(간헐적)인지? (간헐적이면 retry로 대부분 해결될
   가능성이 높고, 항상 재현이면 다른 상시 원인을 더 찾아야 함)

### 구현 대상 파일
- `app/widgets/export_dialog.py` (주 수정 — retry 헬퍼)
- `app/core/auto_labeler.py` (보조 수정 — `with` 감싸기, 선택적)

### 검증 골든 패스
1. (자동화 어려움) 정상 환경에서 내보내기 골든패스(JSON/YOLO/COCO 각 포맷, 이미지

   영향 없어야 함.
2. 가능하면 의도적으로 파일 잠금을 재현해보는 스크립트(예: 별도 프로세스가 `img_path`를
   `open(path, "rb")`로 잠깐 잡고 있다가 200ms 후 놓는 시뮬레이션)로 retry가 실제로
   성공 복구하는지 단위 테스트 수준에서 확인.
3. `auto_labeler.py` 변경 시 자동 라벨링 골든패스(미라벨 이미지 전체 스캔 → 미리보기 →
   커밋) 회귀 없는지 확인.

## GitHub #15 — 브러시 채우기 시 기존 라벨 경계까지 고려

### 배경
오늘 커밋 `e02cf95`(`fix: 브러시 채우기 시 시작·끝점 강제 연결 제거`)로 `_fill_enclosed()`
가 브러시 궤적 자체만으로 폐곡선을 억지로 만들지 않도록 이미 수정됨. 이번 요청은 그
다음 단계 — **현재 그리는 브러시 궤적(`self._brush_np`)만으로 flood-fill 하는 지금
구조를, 이미 존재하는 다른 어노테이션의 경계도 "벽"으로 참여시켜 확장**하고 싶다는
요청.

### 현재 구조 (`app/widgets/annotation_canvas.py` `_fill_enclosed()`, 937~959행)
- `_finish_brush()`가 `TOOL_BRUSH_FILL`일 때만 호출.
- `mask = self._brush_np.copy()` — **오직 이번 스트로크 궤적만** 대상.
- 이미지 네 모서리 중 궤적이 안 닿은 모서리를 시드로 삼아 `cv2.floodFill`로 외부를
  채우고, 채워지지 않은 나머지(`!= 2`)를 "내부"로 판정해 그 결과를 그대로
  `self._brush_np`에 대입.
- 이후 `_finish_brush()`가 이 결과를 새 `AnnotationItem(type="brush_mask")`로 만들어
  `_resolve_overlap_and_merge()`(1079행)에 넘긴다 — 이 단계에서 **픽셀 독점성**(다른
  어노테이션과 겹치는 픽셀은 다른 쪽에서 제거) + **같은 클래스 연결 병합**
  (`_consolidate_class_region`, connectedComponents 기반, bbox 스코프)이 이미 자동으로
  일어난다.

### 핵심 설계 포인트 — "병합"은 이미 있다, 필요한 건 "벽 확장"뿐
`_consolidate_class_region()`이 이미 같은 클래스의 서로 인접/겹치는 brush_mask들을
자동으로 하나의 마스크로 합친다(connectedComponents connectivity=4). 즉 **새로 채워진
영역이 기존 같은 클래스 어노테이션과 픽셀 단위로 맞닿기만 하면, 별도 병합 로직을
새로 짤 필요 없이 기존 커밋 파이프라인이 알아서 하나로 합쳐준다.** 따라서 이번 이슈의
실제 구현 범위는 `_fill_enclosed()` 하나로 좁혀진다:

1. **벽(wall) 마스크 확장**: `self._brush_np`(이번 궤적)만이 아니라, 근처의 기존
   어노테이션 마스크를 OR로 합친 것을 flood-fill 입력으로 사용.
2. **커밋되는 새 마스크는 "순증분만"**: flood-fill 결과(`filled`)에서 **기존
   어노테이션이 원래 차지하던 픽셀은 제외**하고, `(이번 궤적이 그린 픽셀) OR
   (flood-fill로 새로 드러난 빈 공간)`만 `self._brush_np`로 남긴다. 즉:
   ```
   walls = brush_np | existing_same_class_masks_or   # flood-fill 입력
   filled = floodfill_interior(walls)                 # 기존 알고리즘 그대로, 입력만 확장
   new_region = filled & ~existing_same_class_masks_or  # 기존 어노테이션 몫 제외
   self._brush_np = new_region
   ```
   이렇게 하면 기존 어노테이션은 "경계 역할"만 하고 **그 내부 픽셀이 새 어노테이션
   ID로 흡수되는 일이 없다** — task brief가 명시한 회귀 위험(기존 라벨의 annotation_id가
   이번 스트로크의 새 ID로 치환/흡수되는 것)을 원천 차단. 대신 `new_region`이 기존
   어노테이션과 맞닿아 있으므로, 커밋 직후 `_consolidate_class_region()`이 자동으로
   기존 어노테이션과 하나로 합쳐 **사용자 입장에서는 하나의 확장된 라벨**로 보인다
   (내부적으로 새 annotation_id가 최종 병합 마스크의 ID가 될 수 있는데, 이는 기존
   병합 로직의 기존 동작 그대로 — 이번 이슈가 새로 만드는 부작용이 아님).

### 성능 — bbox 스코프 최적화 (필수)
전체 이미지 해상도로 모든 기존 어노테이션을 매 스트로크마다 OR로 합치면, 오늘 이미
`_OverlayWorker`/`_resolve_overlap_and_merge`가 겪었던 것과 같은 함정(20MP 전체 배열
반복 계산)을 반복하게 된다. `_resolve_overlap_and_merge`/`_consolidate_class_region`이
쓰는 기존 패턴(brush_bbox 기준 서브영역만 처리)을 그대로 재사용해야 한다:

1. **후보 축소** — 기존 어노테이션 중 **클래스가 같고**, 자신의 bbox가 "이번 스트로크
   bbox를 여유값만큼 padding한 영역"과 겹치는 것만 후보로 남긴다(bbox-vs-bbox 비교는
   픽셀 순회 없이 O(1)). 후보가 0개면 지금과 동일하게 동작(회귀 없음, 즉시 폴백).
2. **작업 캔버스 축소** — flood-fill을 이미지 전체 크기가 아니라, "이번 스트로크
   bbox ∪ 후보 어노테이션들의 bbox"를 여유값만큼 padding한 **로컬 사각형**으로 잘라서
   수행한다. 시드는 이 로컬 사각형의 네 모서리 중 벽이 아닌 곳으로 선택(기존 알고리즘의
   "이미지 네 모서리" 대신 "작업 영역 네 모서리").
   - **위험 요소**: 이 로컬 사각형이 실제 채워야 할 영역보다 작으면(패딩 부족),
     사각형의 네 모서리 자체가 이미 "벽 안쪽"에 들어가 버려 올바른 외부 시드를 못
     찾을 수 있다(오탐 — 잘못 채워지거나 전혀 안 채워짐). **완화책**: 네 모서리가
     전부 벽(1)이면 패딩을 2배로 늘려 재시도(최대 N회, 예: 3회) → 그래도 실패하면
     기존 전체-이미지 방식으로 폴백(느리지만 항상 정답).
3. `same-class` 필터링, bbox 후보 축소, 병합 등은 이미 `_resolve_overlap_and_merge`/
   `_consolidate_class_region`이 쓰는 코드 스타일과 유사하므로 그대로 관례를 따르면
   된다 — 새 자료구조/알고리즘 불필요.

### 사용자 확인 필요 — 결정 대기 등록 대상

1. **벽 범위: 같은 클래스만? 모든 클래스?** — 원문("기존 윤곽까지 같이 생각")은
   "이미 라벨링된 영역 옆에 이어서 그리기"(같은 클래스 확장) 예시로 설명됐지만, 문자
   그대로 읽으면 "어떤 클래스든 이미 있는 라벨의 경계는 다 벽"으로 읽을 수도 있다.
   - **같은 클래스만 벽으로 취급**하면: 다른 클래스 라벨 옆에 브러시 채우기를 할 때는
     지금처럼 그 라벨 위에 겹쳐 칠해지고(픽셀 독점성 단계에서 자동으로 다른 클래스
     쪽이 양보), 이슈가 언급한 "이어 그리기" 시나리오만 정확히 해결.
   - **모든 클래스를 벽으로 취급**하면: 브러시 채우기가 절대로 다른 라벨 내부로
     "침범"하지 못하게 되는 동작 변화가 생김(현재는 침범 후 자동으로 픽셀을 뺏어가는
     방식) — 이건 이슈 범위를 넘어서는 별도의 동작 변경일 수 있어 사용자 의도 확인 필요.
   - **권장(잠정)**: 같은 클래스만. 근거: 이슈 원문 예시가 "같은 라벨 이어 그리기"이고,
     다른 클래스까지 벽으로 넓히면 회귀 리스크(기존 겹침 처리 동작 변경)가 커짐.
2. **패딩 마진 기본값** — "근처" 기존 라벨을 얼마나 넓은 반경까지 벽 후보로 인식할지
   기본값이 필요하다(너무 좁으면 이슈가 원하는 시나리오를 못 잡고, 너무 넓으면 성능
   저하 + 의도치 않은 먼 라벨까지 벽으로 끌어들일 위험). 브러시 크기의 배수(예: 브러시
   반경의 4~8배) 또는 고정 픽셀(예: 50~100px) 중 어느 쪽을 원하는지, 혹은 임의값으로
   진행해도 괜찮은지 확인 필요.

이 2건은 `docs/decisions-needed.md`에 등록한다(구현 진행에 필수적인 분기점이라
사용자 확인 전 구현 착수 보류 권장 — #16/#17과 달리 답변에 따라 구현 로직 자체가
달라짐).

   벤치마크(오늘 R6/#6-B 라운드가 쓴 방식 재사용).
6. 폴백 경로(로컬 사각형 네 모서리가 전부 벽인 경우) 강제 유발 테스트 — 패딩 확장
   재시도 후에도 실패하면 전체-이미지 방식으로 안전하게 폴백하는지.

## GitHub #12 — "브러시는 그리는 도구일 뿐, annotation에서 분류할 필요 없다"

### 조사 결과 — 원문이 가리키는 지점을 코드로 좁힘

세 가지 가설을 코드 기준으로 확인:

**(a) `class_panel.py`가 브러시/폴리곤을 구분해서 보여주는가?**
→ `app/widgets/class_panel.py`는 클래스(이름/색상) 목록만 다루고 어노테이션 인스턴스나
그 타입(polygon/brush_mask)을 전혀 표시하지 않음. **기각.**

**(b) 어노테이션 목록/사이드바가 타입을 그대로 노출하는가?**
→ **확인됨.** `app/tabs/labeling_tab.py` `_refresh_ann_list()`(507~541행)가 어노테이션
목록 패널(`self._ann_list`, `QListWidget`)의 각 항목 텍스트를 다음과 같이 만든다:
```python
type_label = "Poly" if ann.type == "polygon" else "Mask"
...
target.append((ann.annotation_id, f"#{idx}  [{type_label}] {name}{pos_info}", color))
```
즉 같은 클래스라도 폴리곤으로 그린 것과 브러시로 그린 것이 리스트에
`#1 [Poly] 클래스명`, `#2 [Mask] 클래스명`처럼 **서로 다른 태그를 달고 별개 항목으로**
표시된다. 이게 "브러시가 도구일 뿐인데 분류당하는 느낌"의 가장 직접적인 근거로 보인다.

**(c) 같은 클래스인데 polygon과 brush_mask가 타입이 다르다는 이유로 병합이 안 되는가?**
→ **확인됨(사실관계).** `_resolve_overlap_and_merge()`/`_consolidate_class_region()`
(`annotation_canvas.py` 1079~1204행)은 새로 커밋되는 어노테이션이 `type == "brush_mask"`
일 때만 동작하고, 병합 대상도 `ann.type == "brush_mask"`인 것끼리만 묶는다. **폴리곤은
아예 병합 대상에서 제외**된다 — 같은 클래스의 폴리곤과 브러시 마스크가 서로 맞닿아
있어도 항상 별개의 어노테이션 항목 2개로 남는다(단, 지우개로 폴리곤을 건드리면
`_rasterize_polygons_touching()`이 그 폴리곤을 brush_mask로 강제 변환하는 예외 경로는
있음 — 하지만 이건 지우개 전용이고 사용자가 겪는 일반적인 "이어 그리기" 상황과는 무관).
이 자체는 자료구조상 자연스러운 제약(폴리곤=점 목록, brush_mask=래스터 마스크, 공통
표현이 없어 "하나의 항목으로 합치기"가 폴리곤→마스크 변환 없이는 불가능)이지만,
**(b)의 UI 노출과 결합되면** 사용자에게는 "브러시와 폴리곤이 다른 종류의 것으로
취급당한다"는 인상을 강하게 준다.

### 가장 유력한 결론
(b)가 원문과 가장 직접적으로 일치하는 원인 — **어노테이션 목록에 `[Poly]`/`[Mask]`
태그가 노출되는 것 자체가 "도구별 분류"로 읽힌다.** (c)는 그 인상을 강화하는 배경
요인(같은 클래스라도 그리기 도구가 다르면 항상 별개 항목으로 남음)이지만, 자료구조
제약상 완전히 없애기는 어렵고 UI 노출 문제보다 손대는 범위가 훨씬 큼.

### 제안 스코프 (2가지 옵션, 사용자 확인 필요)
- **옵션 A (저비용, 권장)**: `_refresh_ann_list()`의 표시 텍스트에서 `[Poly]`/`[Mask]`
  타입 태그만 제거. 클래스명 + 순번 + (폴리곤이면) 위치정보만 남긴다. 내부 데이터
  구조(`AnnotationItem.type`)는 그대로 유지 — 저장 포맷/렌더링/병합 로직 변경 없음,
  순수 표시 문자열 변경. 리스크 최소.
- **옵션 B (고비용, 비권장 잠정)**: 같은 클래스의 폴리곤+브러시가 서로 겹치거나 맞닿을
  때도 하나의 "논리적 라벨"로 묶어 보여주거나 자동 병합. 폴리곤을 브러시 마스크로
  변환해야 하므로 좌표 정밀도 손실(벡터→래스터)이 생기고, 기존 폴리곤 편집(꼭짓점
  드래그 등) 워크플로우와 충돌 가능성 있음 — 별도 스파이크/설계 라운드 필요할 정도로
  범위가 큼.

### 사용자에게 물어볼 질문 (원문이 짧아 재현 조건 불명확 — 결정 대기 등록)
1. "분류할 필요 없다"는 게 정확히 **어느 화면**을 보고 한 말인지 확인 필요 —
   라벨링 탭 우측 어노테이션 목록 패널의 `[Poly]`/`[Mask]` 태그를 보고 한 말이 맞는지
   (스크린샷 있으면 가장 확실).
2. 맞다면, 원하는 결과가 **옵션 A**(태그만 제거, 목록 항목 개수는 그대로)인지, 아니면
   **옵션 B**(같은 클래스면 그리기 도구와 무관하게 하나의 항목으로 합쳐 보이길 원함)
   인지 확인 필요 — 둘은 구현 비용·리스크 차이가 크다.
3. (참고용) 만약 답이 옵션 B라면, GitHub #15(브러시 채우기 벽 확장)와 함께 "같은 클래스
   병합" 관련 작업이 겹치므로 순서/스코프 조율이 필요함을 사용자에게 미리 알림.

이 항목은 `docs/decisions-needed.md`에 등록한다 — 구현 스코프 자체가 답변에 따라
크게 달라지므로 답변 전 구현 착수 보류 권장.

### 사용자 결정 완료 (2026-08-27)
**옵션 B — 같은 클래스면 그리기 도구(폴리곤/브러시) 무관하게 하나의 논리적 라벨로
자동 병합.** 권장했던 저비용 옵션A(태그 제거만)가 아니라 고비용 옵션B로 확정.

옵션B는 위 "제안 스코프" 절에서 이미 "폴리곤을 브러시 마스크로 변환해야 하므로
좌표 정밀도 손실 발생, 기존 폴리곤 편집 워크플로우와 충돌 가능성 있어 별도
스파이크/설계 라운드 필요할 정도로 범위가 큼"이라고 명시한 항목이다 — 구현
착수 전 상세 설계(변환 트리거 시점, undo/redo 영향, 편집 중인 폴리곤과의 충돌
방지, GitHub #15의 같은-클래스 벽 확장 기능과의 상호작용)를 기획 라운드로
한 번 더 거친다.
