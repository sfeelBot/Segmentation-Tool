## GitHub #17 — 이미지 목록 다중선택 → Ctrl+C 파일명 복사

### 문제 정의
이미지 브라우저(`app/widgets/image_browser.py`)의 `_tree`(`QTreeWidget`)는 이미
`ExtendedSelection`(Ctrl/Shift 다중선택 가능, GitHub #8에서 확인됨)이지만, 키보드
단축키 핸들러가 전혀 없다(`keyPressEvent`/`eventFilter` 미구현 확인). Ctrl+C를 눌러도
아무 반응이 없다.

### 스코프
- **대상 파일**: `app/widgets/image_browser.py` 1곳만 수정.
- **구현 방식 제안**: `_tree`는 `QTreeWidget` 인스턴스를 직접 생성해 쓰는 구조라
  (`ImageBrowser.__init__`→`_build_ui()`에서 `self._tree = QTreeWidget()`), 서브클래싱
  대신 `self._tree.installEventFilter(self)` + `ImageBrowser.eventFilter()`에서
  `QEvent.Type.KeyPress` + `Qt.Key.Key_C` + `ControlModifier` 조합을 가로채는 방식이
  가장 적은 변경으로 끝난다(새 클래스 불필요).
- **복사 대상**: "파일명들"이라는 원문에 따라 **파일명만**(디렉토리 경로 제외).
  **확장자 포함**으로 제안 — `_on_delete()`의 확인 다이얼로그가 이미 `p.name`(확장자
  포함, 예: `img001.jpg`)으로 미리보기를 표시하는 기존 관례와 일치시킴. 별도 결정 불필요
  (사소한 선택, 위 관례 재사용이면 충분).
- **정렬 순서**: `_tree.selectedItems()`가 반환하는 순서 그대로 사용(일반적으로 트리
  표시(문서) 순서와 일치) — 별도 재정렬 로직 불필요.
- **구분자**: 줄바꿈(`\n`)으로 join 후 `QApplication.clipboard().setText()`.
- **적용 조건**: 선택된 항목이 0개면 아무 동작 안 함(빈 문자열 복사 방지).

### 참고 — 유사 패턴 기존 코드
`app/widgets/settings_dialog.py`에 이미 `QApplication.clipboard().setText()` 클립보드
복사 패턴이 있고(GitHub #4에서 재사용됨), 이번에도 그대로 재사용 가능 — 신규 유틸 불필요.

### 결정 필요 사항
없음 — 바로 구현 가능.

### 검증 골든 패스
1. 이미지 브라우저에서 Ctrl/Shift로 2개 이상 선택 → Ctrl+C → 메모장 등에 붙여넣기 →
   줄바꿈으로 구분된 파일명(확장자 포함) 목록 확인.
2. 단일 선택 상태에서 Ctrl+C → 파일명 1개만 복사되는지 확인.
3. 선택 없는 상태(포커스만 있고 아무것도 선택 안 됨)에서 Ctrl+C → 크래시/빈 복사 없는지 확인.
4. 검색/정렬 필터가 걸린 상태에서도 정상 동작하는지 확인(필터된 `_paths` 기준으로
   보이는 항목만 복사 대상이 되는지).
5. 다른 위젯(검색창 `QLineEdit` 등)에 포커스가 있을 때 Ctrl+C를 눌러도 이미지 브라우저의
   복사 로직이 오동작하지 않는지(이벤트 필터가 `_tree`에만 걸려 있어야 함) 확인.

## GitHub #16 — 내보내기 실패 (PermissionError, WinError 32)

### 배경 재확인
사용자가 첨부한 실제 크래시 로그는 `self._pairs`를 참조하는 **구버전 코드** 기준이다
(오늘 커밋 `7dabdb5`로 `export_dialog.py`가 `self._pairs`→`self._image_paths`로 이미
리팩터링됨, `docs/agents/implementation-log.md` 참고 — 이건 MemoryError 문제 수정이었고
이번 이슈와는 무관). 하지만 **PermissionError 자체(`shutil.copy2`가 소스 이미지 파일을
읽지 못함)는 그 리팩터링과 별개의 버그이며, 현재 HEAD 코드에도 그대로 남아 있다.**

### 조사 결과

#### 재현 여부
**로컬 재현 실패** — 이 세션 환경에서는 실제 OS 레벨 파일 잠금을 인위적으로 만들 수
없어 코드 감사(정적 분석)로만 원인을 좁혔다. 사용자 환경 자체를 재현할 방법(백신 종류,
OneDrive 등 클라우드 동기화 여부, Explorer 미리보기 창 열림 여부)을 알 수 없어 실측
재현은 이번 라운드 범위 밖.

#### 원인 후보 — 순위별 정리

**1순위 (외부 프로세스, 가능성 높음)** — Windows 에러 메시지 자체("다른 프로세스가
파일을 사용 중")가 이 진단을 직접 뒷받침한다:
- Windows 탐색기 미리보기 창/썸네일 캐시 생성이 이미지 파일을 순간적으로 잠금
- 백신 실시간 검사가 새로 접근된 이미지 파일을 스캔하는 동안 잠금
- OneDrive/구글드라이브 등 클라우드 동기화 클라이언트가 `images_dir`이 동기화 폴더
  안에 있을 경우 업로드/온디맨드 다운로드 중 파일을 잠금
- 사용자 환경 경로가 `d:\SW python\46-corrisioin-seg-tool`로 원래 리포지토리와 다른
  폴더명 — 이 프로젝트를 복제/포크해 실사용 배포 중인 것으로 보이며, 그 환경의 폴더
  위치(동기화 폴더 여부 등)를 알 수 없다는 점도 이 가설을 뒷받침(정보 부족일 뿐 반증은
  아님).

**2순위 (내부, 가능성 낮음)** — 이 앱 자체가 파일 핸들을 쥐고 있을 가능성을 코드
감사로 확인:
- `app/widgets/export_dialog.py`의 `_image_size()`는 이미 `with Image.open(path) as im:`
  으로 안전하게 닫힘. `_export_json/_export_yolo/_export_coco` 전부 `load_annotations()`
  (JSON 파일, 이미지 아님)만 열고 이미지 자체는 `shutil.copy2`가 읽기 전용으로 여는 것이
  전부 — export_dialog.py 자체에는 이미지 파일을 열어둔 채 방치하는 코드가 없음.
- `app/core/dataset.py`의 `_load_cached()`(학습 데이터로더 LRU 캐시)가
  `Image.open(img_path).convert("RGB")` 결과 객체를 캐시에 **장기 보관**하지만, PIL의
  `Image.load()`(= `.convert()`가 내부적으로 호출)는 `_exclusive_fp=True`(파일 경로로
  직접 열었을 때)인 경우 픽셀 데이터를 다 읽은 직후 OS 파일 핸들을 즉시 닫는다 — 캐시에
  남는 것은 디코딩된 픽셀 배열(메모리)이지 열린 파일 핸들이 아님. **이 캐시는 OS 레벨
  파일 잠금의 원인이 아닌 것으로 판단.**
- `app/core/auto_labeler.py:70` `img = Image.open(str(img_path))` — `.convert()`/`.load()`
  를 호출하지 않고 `.width`/`.height`(헤더 정보, lazy 로드라 파일을 다 읽지 않음)만 접근함.
  이 경우 OS 파일 핸들이 **다음 루프 반복까지** 열려 있을 수 있다(CPython 참조 카운트로
  다음 `img = Image.open(...)` 대입 시점에 이전 객체가 GC돼 닫힘). 다만 Windows에서
  CPython 내장 `open()`/PIL이 기본으로 사용하는 공유 모드는 다른 프로세스의 읽기/쓰기를
  막지 않는 "deny-none"이 기본값이라, 이 앱 자신의 핸들이 **자기 자신의 `shutil.copy2`
  호출**을 막을 개연성은 낮다(같은 프로세스 내 협조적 접근이라면 더더욱). 다만 자동
  라벨링(전체 프로젝트 순회, 백그라운드 `QThread`)이 실행되는 도중 사용자가 **정확히 같은
  이미지**를 대상으로 내보내기를 동시에 실행하는 경쟁 상황이면 이론상 완전히 배제할 수는
  없음 — 근본 원인일 가능성은 낮지만(외부 프로세스 가설보다 약함), 위생 차원에서 고치는
  것을 권장.
- `app/widgets/annotation_canvas.py:330` `self._pixmap = QPixmap(str(path))` — Qt의
  이미지 로더는 디코딩 즉시 내부적으로 파일을 닫는 구조라(Qt가 직접 여는 `QFile` 기반),
  라벨링 탭에 이미지가 표시돼 있다고 해서 파일 핸들이 계속 열려있지는 않을 것으로 판단.
- `app/widgets/export_dialog.py`의 `ExportDialog`는 `main_window.py`에서
  `dlg.exec()`(모달)로 열린다 — 메인 스레드 위젯 조작은 막히지만, 학습/추론/자동라벨링의
  백그라운드 `QThread` 워커는 모달 다이얼로그와 무관하게 계속 실행될 수 있다. 즉 "내보내기
  중 다른 작업이 그 이미지를 동시에 건드릴 수 없다"는 보장이 앱 안에 없다 — 사용자가
  학습/추론/자동라벨링을 백그라운드에서 돌리는 도중 내보내기를 실행했을 가능성도 배제 못함
  (사용자에게 재현 조건으로 확인 필요, 아래 질문 참고).

**결론**: 내부 코드에 "명백한 상시 파일 잠금 버그"는 발견되지 않았다. 가장 유력한
원인은 앱 외부 요인(백신/탐색기/동기화 클라이언트)이며, 내부적으로는 `auto_labeler.py`
비-`with` 패턴이 이론적 가능성으로만 남는다.

### 제안하는 수정

**주 수정 (원인 불명이어도 항상 유효한 방어책)** — `export_dialog.py`의
`shutil.copy2(img_path, img_out / img_path.name)` 호출 3곳(`_export_json`,
`_export_yolo`, `_export_coco`)을 짧은 retry+backoff 헬퍼로 감싼다. 외부 프로세스의
파일 잠금은 대개 수십~수백 ms 안에 해제되는 일시적 현상이므로, 예: 3회 재시도
(즉시 실패 시 100ms → 300ms → 900ms 대기 후 재시도), `PermissionError`/`OSError`만
잡고 마지막 시도도 실패하면 그대로 raise(기존 `run()`의 `except Exception` →
`error` 시그널 → `QMessageBox.critical` 경로는 그대로 유지, 예외를 삼키지 않음 —
CLAUDE.md "core 모듈은 예외를 그대로 raise" 원칙 준수). 3개 함수가 동일 패턴을
반복하므로 헬퍼 함수 하나(`_copy_with_retry(src, dst)`)로 통합해 중복 제거.

**보조 수정 (위생, 낮은 우선순위)** — `app/core/auto_labeler.py:70`의
`img = Image.open(str(img_path))`를 `with Image.open(str(img_path)) as img:`로 감싸
루프 반복 사이 파일 핸들이 열려 있는 구간 자체를 제거. 근본 원인일 개연성은 낮지만
고치는 비용이 1줄 수준이라 겸사겸사 처리 권장.

**하지 않는 것**: `dataset.py`의 LRU 캐시는 설계 의도된 성능 최적화이고 파일 핸들을
쥐고 있지 않음이 확인됐으므로 손대지 않음.

### 사용자에게 확인하면 좋을 질문 (선택, 결정 대기 등록 대상 아님 — 구현 진행을
막을 필요는 없음)
1. 내보내기 실패 당시 프로젝트의 `images/` 폴더가 OneDrive 등 클라우드 동기화 폴더

3. 내보내기 실행과 동시에 학습/추론/자동 라벨링을 백그라운드에서 돌리고 있었는지?
4. 실패가 항상 재현되는지, 아니면 가끔(간헐적)인지? (간헐적이면 retry로 대부분 해결될
   가능성이 높고, 항상 재현이면 다른 상시 원인을 더 찾아야 함)

### 구현 대상 파일
- `app/widgets/export_dialog.py` (주 수정 — retry 헬퍼)

### 검증 골든 패스

2. 가능하면 의도적으로 파일 잠금을 재현해보는 스크립트(예: 별도 프로세스가 `img_path`를
   `open(path, "rb")`로 잠깐 잡고 있다가 200ms 후 놓는 시뮬레이션)로 retry가 실제로
   성공 복구하는지 단위 테스트 수준에서 확인.
3. `auto_labeler.py` 변경 시 자동 라벨링 골든패스(미라벨 이미지 전체 스캔 → 미리보기 →
   커밋) 회귀 없는지 확인.

## GitHub #15 — 브러시 채우기 시 기존 라벨 경계까지 고려

### 배경
오늘 커밋 `e02cf95`(`fix: 브러시 채우기 시 시작·끝점 강제 연결 제거`)로 `_fill_enclosed()`
가 브러시 궤적 자체만으로 폐곡선을 억지로 만들지 않도록 이미 수정됨. 이번 요청은 그
다음 단계 — **현재 그리는 브러시 궤적(`self._brush_np`)만으로 flood-fill 하는 지금
구조를, 이미 존재하는 다른 어노테이션의 경계도 "벽"으로 참여시켜 확장**하고 싶다는
요청.

### 현재 구조 (`app/widgets/annotation_canvas.py` `_fill_enclosed()`, 937~959행)
- `_finish_brush()`가 `TOOL_BRUSH_FILL`일 때만 호출.
- `mask = self._brush_np.copy()` — **오직 이번 스트로크 궤적만** 대상.
- 이미지 네 모서리 중 궤적이 안 닿은 모서리를 시드로 삼아 `cv2.floodFill`로 외부를
  채우고, 채워지지 않은 나머지(`!= 2`)를 "내부"로 판정해 그 결과를 그대로
  `self._brush_np`에 대입.
- 이후 `_finish_brush()`가 이 결과를 새 `AnnotationItem(type="brush_mask")`로 만들어
  `_resolve_overlap_and_merge()`(1079행)에 넘긴다 — 이 단계에서 **픽셀 독점성**(다른
  어노테이션과 겹치는 픽셀은 다른 쪽에서 제거) + **같은 클래스 연결 병합**
  (`_consolidate_class_region`, connectedComponents 기반, bbox 스코프)이 이미 자동으로
  일어난다.

### 핵심 설계 포인트 — "병합"은 이미 있다, 필요한 건 "벽 확장"뿐
`_consolidate_class_region()`이 이미 같은 클래스의 서로 인접/겹치는 brush_mask들을
자동으로 하나의 마스크로 합친다(connectedComponents connectivity=4). 즉 **새로 채워진
영역이 기존 같은 클래스 어노테이션과 픽셀 단위로 맞닿기만 하면, 별도 병합 로직을
새로 짤 필요 없이 기존 커밋 파이프라인이 알아서 하나로 합쳐준다.** 따라서 이번 이슈의
실제 구현 범위는 `_fill_enclosed()` 하나로 좁혀진다:

1. **벽(wall) 마스크 확장**: `self._brush_np`(이번 궤적)만이 아니라, 근처의 기존
   어노테이션 마스크를 OR로 합친 것을 flood-fill 입력으로 사용.
2. **커밋되는 새 마스크는 "순증분만"**: flood-fill 결과(`filled`)에서 **기존
   어노테이션이 원래 차지하던 픽셀은 제외**하고, `(이번 궤적이 그린 픽셀) OR
   (flood-fill로 새로 드러난 빈 공간)`만 `self._brush_np`로 남긴다. 즉:
   ```
   walls = brush_np | existing_same_class_masks_or   # flood-fill 입력
   filled = floodfill_interior(walls)                 # 기존 알고리즘 그대로, 입력만 확장
   new_region = filled & ~existing_same_class_masks_or  # 기존 어노테이션 몫 제외
   self._brush_np = new_region
   ```
   이렇게 하면 기존 어노테이션은 "경계 역할"만 하고 **그 내부 픽셀이 새 어노테이션
   ID로 흡수되는 일이 없다** — task brief가 명시한 회귀 위험(기존 라벨의 annotation_id가
   이번 스트로크의 새 ID로 치환/흡수되는 것)을 원천 차단. 대신 `new_region`이 기존
   어노테이션과 맞닿아 있으므로, 커밋 직후 `_consolidate_class_region()`이 자동으로
   기존 어노테이션과 하나로 합쳐 **사용자 입장에서는 하나의 확장된 라벨**로 보인다
   (내부적으로 새 annotation_id가 최종 병합 마스크의 ID가 될 수 있는데, 이는 기존
   병합 로직의 기존 동작 그대로 — 이번 이슈가 새로 만드는 부작용이 아님).

### 성능 — bbox 스코프 최적화 (필수)
전체 이미지 해상도로 모든 기존 어노테이션을 매 스트로크마다 OR로 합치면, 오늘 이미
`_OverlayWorker`/`_resolve_overlap_and_merge`가 겪었던 것과 같은 함정(20MP 전체 배열
반복 계산)을 반복하게 된다. `_resolve_overlap_and_merge`/`_consolidate_class_region`이
쓰는 기존 패턴(brush_bbox 기준 서브영역만 처리)을 그대로 재사용해야 한다:

1. **후보 축소** — 기존 어노테이션 중 **클래스가 같고**, 자신의 bbox가 "이번 스트로크
   bbox를 여유값만큼 padding한 영역"과 겹치는 것만 후보로 남긴다(bbox-vs-bbox 비교는
   픽셀 순회 없이 O(1)). 후보가 0개면 지금과 동일하게 동작(회귀 없음, 즉시 폴백).
2. **작업 캔버스 축소** — flood-fill을 이미지 전체 크기가 아니라, "이번 스트로크
   bbox ∪ 후보 어노테이션들의 bbox"를 여유값만큼 padding한 **로컬 사각형**으로 잘라서
   수행한다. 시드는 이 로컬 사각형의 네 모서리 중 벽이 아닌 곳으로 선택(기존 알고리즘의
   "이미지 네 모서리" 대신 "작업 영역 네 모서리").
   - **위험 요소**: 이 로컬 사각형이 실제 채워야 할 영역보다 작으면(패딩 부족),
     사각형의 네 모서리 자체가 이미 "벽 안쪽"에 들어가 버려 올바른 외부 시드를 못
     찾을 수 있다(오탐 — 잘못 채워지거나 전혀 안 채워짐). **완화책**: 네 모서리가
     전부 벽(1)이면 패딩을 2배로 늘려 재시도(최대 N회, 예: 3회) → 그래도 실패하면
     기존 전체-이미지 방식으로 폴백(느리지만 항상 정답).
3. `same-class` 필터링, bbox 후보 축소, 병합 등은 이미 `_resolve_overlap_and_merge`/
   `_consolidate_class_region`이 쓰는 코드 스타일과 유사하므로 그대로 관례를 따르면
   된다 — 새 자료구조/알고리즘 불필요.

### 사용자 확인 필요 — 결정 대기 등록 대상

1. **벽 범위: 같은 클래스만? 모든 클래스?** — 원문("기존 윤곽까지 같이 생각")은
   "이미 라벨링된 영역 옆에 이어서 그리기"(같은 클래스 확장) 예시로 설명됐지만, 문자
   그대로 읽으면 "어떤 클래스든 이미 있는 라벨의 경계는 다 벽"으로 읽을 수도 있다.
   - **같은 클래스만 벽으로 취급**하면: 다른 클래스 라벨 옆에 브러시 채우기를 할 때는
     지금처럼 그 라벨 위에 겹쳐 칠해지고(픽셀 독점성 단계에서 자동으로 다른 클래스
     쪽이 양보), 이슈가 언급한 "이어 그리기" 시나리오만 정확히 해결.
   - **모든 클래스를 벽으로 취급**하면: 브러시 채우기가 절대로 다른 라벨 내부로
     "침범"하지 못하게 되는 동작 변화가 생김(현재는 침범 후 자동으로 픽셀을 뺏어가는
     방식) — 이건 이슈 범위를 넘어서는 별도의 동작 변경일 수 있어 사용자 의도 확인 필요.
   - **권장(잠정)**: 같은 클래스만. 근거: 이슈 원문 예시가 "같은 라벨 이어 그리기"이고,
     다른 클래스까지 벽으로 넓히면 회귀 리스크(기존 겹침 처리 동작 변경)가 커짐.
2. **패딩 마진 기본값** — "근처" 기존 라벨을 얼마나 넓은 반경까지 벽 후보로 인식할지
   기본값이 필요하다(너무 좁으면 이슈가 원하는 시나리오를 못 잡고, 너무 넓으면 성능
   저하 + 의도치 않은 먼 라벨까지 벽으로 끌어들일 위험). 브러시 크기의 배수(예: 브러시
   반경의 4~8배) 또는 고정 픽셀(예: 50~100px) 중 어느 쪽을 원하는지, 혹은 임의값으로
   진행해도 괜찮은지 확인 필요.

이 2건은 `docs/decisions-needed.md`에 등록한다(구현 진행에 필수적인 분기점이라
사용자 확인 전 구현 착수 보류 권장 — #16/#17과 달리 답변에 따라 구현 로직 자체가
달라짐).

6. 폴백 경로(로컬 사각형 네 모서리가 전부 벽인 경우) 강제 유발 테스트 — 패딩 확장

## GitHub #12 — "브러시는 그리는 도구일 뿐, annotation에서 분류할 필요 없다"

### 조사 결과 — 원문이 가리키는 지점을 코드로 좁힘

세 가지 가설을 코드 기준으로 확인:

**(a) `class_panel.py`가 브러시/폴리곤을 구분해서 보여주는가?**
→ `app/widgets/class_panel.py`는 클래스(이름/색상) 목록만 다루고 어노테이션 인스턴스나
그 타입(polygon/brush_mask)을 전혀 표시하지 않음. **기각.**

**(b) 어노테이션 목록/사이드바가 타입을 그대로 노출하는가?**
→ **확인됨.** `app/tabs/labeling_tab.py` `_refresh_ann_list()`(507~541행)가 어노테이션
목록 패널(`self._ann_list`, `QListWidget`)의 각 항목 텍스트를 다음과 같이 만든다:
```python
type_label = "Poly" if ann.type == "polygon" else "Mask"
...
target.append((ann.annotation_id, f"#{idx}  [{type_label}] {name}{pos_info}", color))
```
즉 같은 클래스라도 폴리곤으로 그린 것과 브러시로 그린 것이 리스트에
`#1 [Poly] 클래스명`, `#2 [Mask] 클래스명`처럼 **서로 다른 태그를 달고 별개 항목으로**
표시된다. 이게 "브러시가 도구일 뿐인데 분류당하는 느낌"의 가장 직접적인 근거로 보인다.

**(c) 같은 클래스인데 polygon과 brush_mask가 타입이 다르다는 이유로 병합이 안 되는가?**
→ **확인됨(사실관계).** `_resolve_overlap_and_merge()`/`_consolidate_class_region()`
(`annotation_canvas.py` 1079~1204행)은 새로 커밋되는 어노테이션이 `type == "brush_mask"`
일 때만 동작하고, 병합 대상도 `ann.type == "brush_mask"`인 것끼리만 묶는다. **폴리곤은
아예 병합 대상에서 제외**된다 — 같은 클래스의 폴리곤과 브러시 마스크가 서로 맞닿아
있어도 항상 별개의 어노테이션 항목 2개로 남는다(단, 지우개로 폴리곤을 건드리면
`_rasterize_polygons_touching()`이 그 폴리곤을 brush_mask로 강제 변환하는 예외 경로는
있음 — 하지만 이건 지우개 전용이고 사용자가 겪는 일반적인 "이어 그리기" 상황과는 무관).
이 자체는 자료구조상 자연스러운 제약(폴리곤=점 목록, brush_mask=래스터 마스크, 공통
표현이 없어 "하나의 항목으로 합치기"가 폴리곤→마스크 변환 없이는 불가능)이지만,
**(b)의 UI 노출과 결합되면** 사용자에게는 "브러시와 폴리곤이 다른 종류의 것으로
취급당한다"는 인상을 강하게 준다.

### 가장 유력한 결론
(b)가 원문과 가장 직접적으로 일치하는 원인 — **어노테이션 목록에 `[Poly]`/`[Mask]`
태그가 노출되는 것 자체가 "도구별 분류"로 읽힌다.** (c)는 그 인상을 강화하는 배경
요인(같은 클래스라도 그리기 도구가 다르면 항상 별개 항목으로 남음)이지만, 자료구조
제약상 완전히 없애기는 어렵고 UI 노출 문제보다 손대는 범위가 훨씬 큼.

### 제안 스코프 (2가지 옵션, 사용자 확인 필요)
- **옵션 A (저비용, 권장)**: `_refresh_ann_list()`의 표시 텍스트에서 `[Poly]`/`[Mask]`
  타입 태그만 제거. 클래스명 + 순번 + (폴리곤이면) 위치정보만 남긴다. 내부 데이터
  구조(`AnnotationItem.type`)는 그대로 유지 — 저장 포맷/렌더링/병합 로직 변경 없음,
  순수 표시 문자열 변경. 리스크 최소.
- **옵션 B (고비용, 비권장 잠정)**: 같은 클래스의 폴리곤+브러시가 서로 겹치거나 맞닿을
  때도 하나의 "논리적 라벨"로 묶어 보여주거나 자동 병합. 폴리곤을 브러시 마스크로
  변환해야 하므로 좌표 정밀도 손실(벡터→래스터)이 생기고, 기존 폴리곤 편집(꼭짓점
  드래그 등) 워크플로우와 충돌 가능성 있음 — 별도 스파이크/설계 라운드 필요할 정도로
  범위가 큼.

### 사용자에게 물어볼 질문 (원문이 짧아 재현 조건 불명확 — 결정 대기 등록)

   라벨링 탭 우측 어노테이션 목록 패널의 `[Poly]`/`[Mask]` 태그를 보고 한 말이 맞는지
   (스크린샷 있으면 가장 확실).

## GitHub #12 — 옵션B 상세 설계 (2026-08-27 기획 라운드2)

### 코드 조사 요약 — 재사용 가능한 기존 패턴 3곳
`app/widgets/annotation_canvas.py`를 다시 정독한 결과, "같은 클래스면 폴리곤↔브러시를
구분하지 않고 병합"이라는 목표는 **이미 존재하는 세 가지 기존 패턴을 그대로 재사용**하는
것으로 달성 가능함을 확인했다 — 새 알고리즘/자료구조가 필요 없다:

1. **`_rasterize_polygons_touching(region_mask)`** (현재 1044행 부근) — 지우개가 어떤
   영역을 지울 때, 그 영역과 **겹치는** 폴리곤을 즉석에서 `brush_mask`로 변환하는 기존
   함수. 폴리곤→마스크 생성 패턴은 재사용할 수 있지만, 현재의
   `(poly_mask & region_mask).any()`는 픽셀 겹침만 찾고 **4-neighbor로 맞닿기만 한
   도형은 찾지 못한다.** 옵션B는 겹침뿐 아니라 상하좌우 1픽셀 인접도 병합해야 하므로
   클래스/bbox 필터와 함께 로컬 4-neighbor 접촉 판정을 새로 추가해야 한다. 대각선으로만
   닿은 픽셀은 `connectivity=4`인 기존 병합 규칙과 일치하도록 접촉으로 보지 않는다.
2. **`_resolve_overlap_and_merge(new_ann)` → `_consolidate_class_region(...)`**
   (1079~1204행) — 새로 커밋된 `brush_mask`가 `self._brush_bbox` 영역 안에서 같은
   클래스의 다른 `brush_mask`와 픽셀이 겹치거나 맞닿으면(`connectedComponents`)
   자동으로 하나의 어노테이션으로 합친다. **이미 "타입 무관 자동 병합"의 절반
   (mask-mask 병합)을 수행 중** — bbox 매개변수를 명시적으로 받을 수 있게 시그니처만
   확장하면 폴리곤 커밋 경로에서도 재사용 가능.
3. **`_flood_erase()`** (1002~1077행) — 이미 "클릭 지점 클래스의 폴리곤들을 전부
   `brush_mask`로 변환 → `connectedComponents`로 병합 그룹 판정"이라는, 이번 기능과
   철학적으로 동일한 패턴을 다른 목적(영역 지우기)으로 이미 구현해 쓰고 있다. 즉 이
   프로젝트는 이미 3곳에서 "필요할 때만 폴리곤을 래스터로 변환해 병합 파이프라인에
   편입"하는 관례를 갖고 있다 — 이번 설계는 그 관례를 커밋(그리기 완료) 시점까지
   넓히는 것뿐이다.

### 1. 병합 트리거 시점 — "표시만 그룹핑"이 아니라 "실제 데이터 병합", 커밋 순간에만
사용자가 확정한 요구사항은 표시상 그룹핑이 아니라 **실제 데이터 병합**이다("같은
클래스면... 하나의 논리적 라벨로 자동 병합되어 보이길 원한다" — 그리고 기존
`_resolve_overlap_and_merge`도 표시가 아니라 `self._annotations` 자체를 줄이는
실제 병합이므로, 폴리곤 쪽만 "표시만 그룹핑"으로 다르게 처리하면 두 타입 간 동작이
비일관적이 된다). 따라서 **"표시만 병합" 저비용 중간 옵션은 채택하지 않는다** —
`_refresh_ann_list()`는 전혀 손대지 않고, `self._annotations` 리스트 자체가 줄어들면
그 결과가 그대로 표시에 반영되는 기존 구조를 그대로 활용한다.

트리거는 브러시가 이미 쓰는 것과 동일한 원칙 — **"커밋(그리기 완료) 순간에만"**:
- 브러시/브러시채우기: `_finish_brush()` (마우스 릴리즈, 스트로크 완료 시 1회)
- 폴리곤: `_close_polygon()` (첫 꼭짓점 근처 클릭 또는 더블클릭으로 폐곡선을 확정하는
  순간, 1회) — `mousePressEvent`(스냅 클릭)와 `mouseDoubleClickEvent` 두 경로가 모두
  `_close_polygon()` 하나로 수렴하므로 트리거 삽입 지점은 단 한 곳이면 된다.
- **그리기 도중(mouse-move)에는 절대 검사하지 않는다** — `self._poly_pts`(폴리곤
  진행 중 클릭점 리스트)는 `_close_polygon()`이 호출되기 전까지 `self._annotations`에
  들어가지 않는 완전히 별개의 임시 버퍼이므로, 애초에 병합 로직이 볼 수 있는 대상이
  아니다(구조적으로 안전 — 별도 가드 불필요).
- **이동(translate, `_translate_selected()`)은 트리거 대상에서 명시적으로 제외**
  (아래 "5. 편집 중 충돌 방지" 절 참고).

### 2. 폴리곤→마스크 변환 — 언제, 어떻게, 얼마나 비싸게
변환은 **병합이 실제로 필요한 경우에만** 일어난다. 대다수(주변에 같은 클래스가 없는
고립된 폴리곤)는 지금처럼 폴리곤인 채로 남아 좌표 정밀도를 그대로 유지한다.

`_close_polygon()`에 추가할 로직(의사코드):
```python
def _close_polygon(self) -> None:
    if len(self._poly_pts) < 3:
        return
    self._push_undo()                      # 기존 위치 그대로 — 변경 전 스냅샷
    points = [(p.x(), p.y()) for p in self._poly_pts]
    pts_arr = np.array([[int(x), int(y)] for x, y in points], dtype=np.int32)
    px, py, pw, ph = cv2.boundingRect(pts_arr)          # 폴리곤 자체 bbox (저비용)
    bx0, by0 = max(0, px - 1), max(0, py - 1)           # 접촉 판정/병합용 margin=1
    bx1 = min(self._img_w, px + pw + 1)
    by1 = min(self._img_h, py + ph + 1)

    # 같은 클래스 후보를 bbox/query-slice로 축소한 뒤 로컬 래스터에서 실제
    # overlap/4-neighbor 접촉을 확인한다. bbox 교차만으로 True를 반환하면 안 된다.
    has_contact = self._has_same_class_contact(
        pts_arr, self._class_id, (bx0, by0, bx1, by1)
    )

    if not has_contact:
        # 기존 동작 그대로 — 폴리곤 유지, 변환 없음, 정밀도 손실 없음
        self._annotations.append(AnnotationItem(
            annotation_id=store.new_id(), class_id=self._class_id,
            type="polygon", order=len(self._annotations), points=points,
        ))
    else:
        # 병합 필요 — 이번 폴리곤 자체를 마스크로 변환해 기존 파이프라인에 편입
        mask = np.zeros((self._img_h, self._img_w), dtype=np.uint8)
        cv2.fillPoly(mask, [pts_arr], 1)
        # 실제로 겹치거나 4-neighbor로 맞닿은 같은 클래스 폴리곤만 변환
        self._rasterize_polygons_touching(mask, class_id=self._class_id, bbox=(bx0, by0, bx1, by1))
        new_ann = AnnotationItem(
            annotation_id=store.new_id(), class_id=self._class_id,
            type="brush_mask", order=len(self._annotations),
            mask=mask, width=self._img_w, height=self._img_h,
        )
        self._annotations.append(new_ann)
        # 기존 브러시 병합 파이프라인 재사용 — bbox를 명시적으로 넘기도록 시그니처 확장
        self._resolve_overlap_and_merge(new_ann, bbox=(bx0, by0, bx1, by1))

    self._poly_pts.clear()
    self._invalidate_overlay()
    self._schedule_save()
    self.update()
```

위 `_has_same_class_contact`는 설명을 위한 이름이며 별도 메서드 추가 여부는 구현자
재량이다. 중요한 계약은 **후보 bbox 교차 → 로컬 실제 접촉 확인 → 접촉이 있을 때만
신규 폴리곤과 접촉 폴리곤을 mask로 변환**하는 3단계다. bbox만 겹치고 실제 픽셀이
떨어진 경우에는 반드시 기존 폴리곤 append 경로로 가야 한다.

필요한 기존 함수 시그니처 확장 (둘 다 하위호환 — 기본값이 기존 동작과 동일):
- `_rasterize_polygons_touching(self, region_mask, class_id: int | None = None, bbox: tuple[int,int,int,int] | None = None)`
  — `class_id` 지정 시 그 클래스의 폴리곤만 변환 대상(기존 지우개 호출부는 `class_id=None`
  그대로 둬서 지금처럼 클래스 무관 **겹침** 변환을 유지). `bbox` 지정 시 폴리곤별
  `cv2.boundingRect`로 후보를 먼저 줄이고, 교차하는 로컬 bbox 크기의 배열에만
  `fillPoly`한 뒤 region의 로컬 슬라이스를 4-neighbor cross kernel로 1회 dilate하여
  실제 겹침/상하좌우 인접을 판정한다. **후보 판정 단계에서 전체 이미지 크기 배열을
  만들면 안 된다.** 실제 접촉이 확정되어 저장형 `brush_mask`로 바꿀 때만 전체 크기
  마스크를 1회 생성한다. 기존 지우개 호출(`bbox=None`)의 의미는 변경하지 않는다.
- `_resolve_overlap_and_merge(self, new_ann, bbox: tuple[int,int,int,int] | None = None)`
  — `bbox`가 없으면 지금처럼 `self._brush_bbox`를 사용(브러시 호출부는 코드 변경 없이
  그대로 동작), `_close_polygon()`은 명시적으로 폴리곤 bbox를 넘긴다.

브러시 쪽(`_finish_brush()`, 911~929행)에도 대칭적으로 한 줄만 추가한다 — **브러시가
같은 클래스 폴리곤에 닿았을 때도 병합되게 하려면 이 방향도 필요**(이슈 원문이
"브러시는 도구일 뿐"이라 했을 때는 브러시→폴리곤 인접도 당연히 포함되는 시나리오):
```python

    # #15는 채움 성공 후 최종 mask의 _mask_bbox(..., margin=1)로 _brush_bbox를 갱신한다.
    # 따라서 일반 브러시와 채우기 모두 여기서는 그 최종 bbox를 그대로 사용한다.
```

지우개(`TOOL_ERASER`) 경로(`_apply_eraser()`)는 건드리지 않는다 — 지우개는 클래스
무관하게 실제로 지워야 하므로 "같은 클래스만 병합"이라는 이번 개념과 무관(기존 결론
그대로 유지).

**성능 — bbox 사전 필터가 필수인 이유**: `_rasterize_polygons_touching`는 원래
지우개 전용(스트로크당 1회, 상대적으로 드묾)이었는데, 이번에 일반 브러시 페인트/채우기
커밋 경로에도 추가하면 **모든 브러시 스트로크마다** 호출된다. bbox 사전 필터 없이
기존 구현 그대로 쓰면 같은 클래스 폴리곤 개수만큼 매 스트로크 `np.zeros(전체이미지)
+ fillPoly + AND`(20MP 스캔)를 반복하게 되어 `GitHub #6-B`/`R1~R6`가 어렵게 잡아둔
"편집당 O(전체 크기)" 회귀를 정확히 재현한다. 위 시그니처에 `bbox` 매개변수를 추가해
`cv2.boundingRect`(폴리곤 점 개수에만 비례, 저렴) 사전 검사로 겹치지 않는 폴리곤은
그 즉시 skip하는 것이 **선택이 아니라 필수 요구사항**이다. 폴리곤 쪽(`_close_polygon`)
경로는 애초에 그리기 완료 시 1회만 호출되므로(스트로크만큼 빈번하지 않음) 상대적으로
여유가 있지만 동일한 최적화를 적용해 일관성을 유지한다.

`_bbox_touches(ann, bx0, by0, bx1, by1)` 헬퍼(신규, 작은 함수)는 타입별 **후보 축소만**
담당한다 — 폴리곤은 `cv2.boundingRect`, `brush_mask`는 자기 tight bbox를 전체 스캔하지
않고 질의 bbox 슬라이스의 `.any()`를 사용한다. bbox 교차를 실제 접촉 판정으로 간주하면
오목한 도형 등에서 불필요한 래스터 변환이 생기므로 금지한다. 최종 판정은 반드시 로컬
래스터의 실제 겹침 또는 4-neighbor 인접으로 수행한다. 이 방식이면 오목한 모양의 bbox가
겹쳐도 실제 픽셀이 떨어져 있으면 폴리곤 타입과 좌표 정밀도가 그대로 보존된다.

### 3. undo/redo 영향 — 기존 스냅샷 방식이 이미 자연스럽게 흡수함 (신규 코드 불필요)
`_push_undo()`(1369~1385행)는 **변경 직전** `self._annotations`의 완전한 스냅샷을
`copy()`(numpy 배열은 memcpy, points는 얕은 리스트 복사)로 떠서 스택에 쌓는다. 이
프로젝트에 **redo는 존재하지 않는다**(grep 확인, `undo()`만 있음) — redo 영향 분석은
해당 없음.

핵심 확인 사항: `_close_polygon()`은 이미 `self._push_undo()`를 **가장 먼저** 호출한
뒤(838행, 변경 전) 나머지 로직을 수행한다 — 이번에 추가하는 "폴리곤→마스크 변환 +
병합" 로직도 전부 이 호출 **다음에** 일어나므로, undo 스택에 쌓이는 스냅샷은 항상
"변환/병합이 전혀 일어나지 않은, 원래 폴리곤들이 폴리곤인 채로 남아있는" 상태다.
따라서 `undo()` 한 번으로:
- 새로 그린 폴리곤이 사라지고,
- 병합 과정에서 `brush_mask`로 강제 변환됐던 기존 폴리곤들도 **원래의 점 목록을 가진
  폴리곤 그대로 되돌아간다** (변환된 게 아니라 애초에 스냅샷에 변환 이전 상태로
  저장돼 있었기 때문 — "복원"이 아니라 "애초에 안 변한 것").
별도의 "역변환(마스크→폴리곤)" 로직을 만들 필요가 전혀 없다 — **기존 undo 아키텍처가
이 변환을 완전히 무료로 흡수한다.** 브러시 쪽(`_finish_brush`)도 마찬가지로 스트로크
시작 시점(`mousePressEvent`, 645행)에 이미 `_push_undo()`가 먼저 호출되므로 동일하게
안전하다.

유일하게 확인해야 할 예외 케이스: `_push_undo()`가 대형 마스크 다수로 인해
`MemoryError`를 잡고 **이번 undo 스텝을 건너뛰는** 기존 폴백(BUG-014 대응, 1377~1382행)
이 있다 — 이 경우 이번 병합으로 인한 변경은 undo 불가능한 채로 남는데, 이는 **이번
기능이 새로 만드는 리스크가 아니라 BUG-014의 기존 한계가 그대로 적용되는 것**뿐이다
(별도 대응 불필요, 기존 문서화된 한계 그대로 인지하고 넘어감).

### 4. GitHub #15와의 상호작용 — 커밋 `7f33695`의 최종 bbox 계약을 그대로 사용
두 기능 모두 `app/widgets/annotation_canvas.py`를 수정하지만 #15는 먼저 커밋되었다.
- **#15**는 `_fill_enclosed()`에서 채우기 성공 경로마다 최종 결과에 대해
  `_mask_bbox(result, margin=1)`을 계산해 `self._brush_bbox`를 갱신한다. 이 margin=1은
  채움으로 원래 스트로크 bbox 밖까지 확장된 픽셀과 그 바로 옆 4-neighbor 후보를
  `_resolve_overlap_and_merge()`가 빠뜨리지 않게 하는 현재 계약이다. #12는 이를 다시
  계산하거나 원래 stroke bbox로 되돌리지 말고, `_fill_enclosed()` 호출 **이후의 최신
  `self._brush_bbox`**를 접촉 판정과 병합에 그대로 넘겨야 한다.
- **#12**는 `_finish_brush()`의 **호출부**(`_fill_enclosed()` 호출 다음 줄에 1줄 추가),
  `_rasterize_polygons_touching()`(시그니처 확장), `_resolve_overlap_and_merge()`
  (시그니처 확장), `_close_polygon()`(신규 로직)을 수정한다 — `_fill_enclosed()`
  **본문은 건드리지 않는다.**

즉 두 라운드는 같은 파일 안에서 **줄 단위로 겹치지 않는다.** 로드맵에 이미 확정된
처리순서(#16→#15→#12→#17)를 그대로 따르면 된다 — **#15 구현이 먼저 커밋된 뒤,
#12 구현 에이전트가 최신 `annotation_canvas.py`를 다시 읽고 나서** 위 변경을
적용하면 줄 번호 변경 정도만 반영하면 되고 실질적 충돌은 없다. (같은 워킹
디렉토리에서 순차 작업이면 애초에 git 충돌 자체가 발생하지 않음 — 병렬 브랜치
작업이 아닌 한.)

**개념적 상호작용 참고**: #15의 flood-fill 벽 후보는 현재 같은 클래스
`brush_mask`만 포함하고 폴리곤은 포함하지 않는다. 따라서 폴리곤이 채우기 벽 자체가
되지는 않지만, #12는 채우기가 끝난 뒤 **최종 마스크 + margin=1 최종 bbox**로 실제
4-neighbor 접촉을 검사해 인접 폴리곤을 병합한다. 채움 모양이 폴리곤을 경계로 삼지 않는
것은 #15의 확정 범위이고, #12는 그 모양을 바꾸지 않는다.

### 5. 편집 중인 폴리곤과의 충돌 방지
코드 조사 결과 **이 앱에는 폴리곤 꼭짓점을 드래그로 편집하는 기능 자체가 아직
구현되어 있지 않다**(`mousePressEvent`/`mouseMoveEvent` 전체를 확인했으나 "꼭짓점
선택 후 드래그" 경로가 없음 — `TOOL_SELECT`가 지원하는 것은 오직 "전체 폴리곤/마스크를
통째로 평행이동"(`_translate_selected()`)뿐). 따라서 task brief가 우려한 "꼭짓점
드래그 도중 병합" 시나리오는 **현재 코드 기준으로는 애초에 발생할 수 없는 상태다.**
다만 두 가지 실제로 존재하는 "진행 중" 상태는 명시적으로 트리거 범위에서 제외해야
한다:

1. **폴리곤을 그리는 도중** (`self._poly_pts`에 점을 계속 추가하는 상태, 아직
   `_close_polygon()` 호출 전) — 위 "1. 병합 트리거 시점"에서 설명했듯 구조적으로
   이미 안전(임시 버퍼는 `_annotations`에 없어 병합 로직이 볼 수 없음). 추가 가드 불필요.
2. **선택한 어노테이션을 드래그로 이동하는 도중** (`_translate_selected()`,
   `mouseMoveEvent`에서 `_move_active=True`일 때 매 프레임 호출) — **이번 범위에서
   명시적으로 제외한다.** 이유 둘:
   - 매 마우스 이동(프레임)마다 병합 후보 탐색을 추가하면 드래그 조작 자체가
     버벅이는 성능 저하가 생긴다(트리거를 "커밋 시점 1회"로 좁힌 전체 설계 원칙과
     정면 충돌).
   - 드래그 도중 어노테이션 타입이 폴리곤→마스크로 갑자기 바뀌면 사용자가 보고 있는
     도중 도형이 재질(벡터→래스터)이 바뀌는 것처럼 보여 혼란스러운 UX가 된다 — 이건
     task brief가 정확히 우려한 리스크와 같은 종류.
   - **결론**: 이동은 지금처럼 폴리곤이면 폴리곤인 채로, 겹쳐 보이더라도 자동
     병합되지 않는다(기존 동작 그대로, 회귀 아님). 이동이 끝난 뒤(`mouseReleaseEvent`
     의 `_move_active=False` 분기)에 1회만 병합 후보 검사를 추가하는 것은 자연스러운
     후속 확장이지만 **이번 라운드 범위 밖**(사용자가 요청한 건 "그리기 도구 구분
     없음"이지 "이동 후 자동 병합"이 아님 — 스코프 확대로 별도 후속 요청 시 재논의).

### 참고 — 남는 잔여 UX 질문 (결정 대기 등록 대상 아님, 정보성 메모)

### 검증 골든 패스 (옵션 B)
1. **기본 회귀 — 고립된 폴리곤/브러시**: 서로 멀리 떨어진 같은 클래스 폴리곤 1개 +
   브러시 1개를 그렸을 때 지금처럼 별개 항목 2개로 남는지(병합 안 됨, 변환 안 됨,
   `ann.type`이 각각 `polygon`/`brush_mask` 그대로 유지되는지 내부 상태로 확인).
2. **핵심 시나리오 A — 브러시로 기존 폴리곤에 이어 칠하기**: 같은 클래스 폴리곤을
   그린 뒤, 그 경계에 맞닿게 브러시로 칠하고 스트로크를 끝내면 어노테이션 목록에
   **하나의 합쳐진 `[Mask]` 항목**으로 보이는지(항목 개수 감소, 픽셀 diff로 원래
   폴리곤 영역이 그대로 보존됐는지 확인).
3. **핵심 시나리오 B — 폴리곤으로 기존 브러시 마스크에 이어 그리기**: 반대 방향(먼저
   브러시로 칠하고, 그 옆에 같은 클래스 폴리곤을 닫아 완성)도 동일하게 병합되는지 확인.
4. **핵심 시나리오 C — 폴리곤 대 폴리곤**: 같은 클래스 폴리곤 2개를 서로 맞닿게
   순서대로 그리면(먼저 A, 다음 B가 A에 닿게) 마찬가지로 하나의 `[Mask]` 항목으로
   합쳐지는지 확인(설계상 poly-poly도 자동으로 커버됨 — 별도 시나리오로 명시 검증).
5. **다른 클래스 인접/겹침 — 현행 동작 보존**: 클래스가 다르면 폴리곤 rasterize/병합
   후보에서 제외되는지 확인한다. 기존 픽셀 독점성은 `brush_mask`끼리의 겹침에는
   나중에 그린 쪽 우선이지만, 폴리곤↔브러시는 폴리곤을 이번 클래스 필터로 변환하지
   않으므로 둘 다 남을 수 있다. #12에서 이를 새로 통일하지 말고 각 조합의 현재 동작을
   회귀 테스트로 고정한다.
6. **undo 왕복**: 시나리오 2~4 각각에서 병합 직후 `undo()` 1회 → 병합 전 상태(원래
   개별 폴리곤/마스크, 타입도 원래대로)로 정확히 복원되는지 픽셀·타입 단위로 확인.
7. **그리기 도중 무결성**: 폴리곤을 그리는 도중(점을 몇 개 찍고 아직 닫지 않은 상태)
   다른 도구로 전환하거나 다른 조작을 해도 진행 중인 점 목록이 병합 로직에 영향받지
   않는지(애초에 트리거되지 않아야 함) 확인.
8. **이동 중 비트리거 확인**: 병합된(또는 병합되지 않은) 어노테이션을 선택해 다른
   위치로 드래그하는 동안 타입이 바뀌지 않고, 이동 후에도 자동 병합이 일어나지
   않는지 확인(이번 라운드 의도된 범위 제외 사항).
9. **성능 — 브러시 스트로크 빈도 회귀 없음**: 같은 클래스 폴리곤이 다수(예: 50개
   이상) 있는 프로젝트에서, 그 폴리곤들과 전혀 안 닿는 곳에 브러시를 칠할 때 스트로크당
   소요 시간이 변경 전과 체감 차이 없는지 벤치마크(`#6-B`/`R6`가 쓴 방식 재사용) —
   bbox 사전 필터가 실제로 효과가 있는지 확인하는 핵심 검증. 테스트에서는 멀리 있는
   후보에 대해 전체 이미지 크기 `np.zeros`/`fillPoly`가 호출되지 않음을 계측하고,
   가까운 후보도 최종 접촉 확정 전에는 로컬 bbox 배열만 생성하는지 확인한다.
10. **#15와의 공존**: 원 스트로크 bbox 밖으로 확장된 채우기 결과가 폴리곤과 겹치거나
    4-neighbor로 맞닿는 사례를 만들고, #15가 갱신한 `margin=1` 최종 bbox가 그대로
    사용되어 정상 병합되는지 확인한다. 원 stroke bbox를 사용하면 실패해야 하는 위치를
    택해 회귀를 확실히 잡는다.
11. **접촉 정의 매트릭스**: brush→poly, poly→brush, poly→poly 각각에 대해
