## BUG-002 배치 근거 (왜 R1에 단독으로 최우선 배치했는가)

- **축이 다르다**: 나머지 7개는 "체감 속도" 문제지만 BUG-002는 "저장한 데이터가 사라진다" — 되돌릴 수 없는 손실. 성능 항목과 같은 우선순위 축으로 비교할 수 없으므로 최상단에 둔다.
- **격리 가능**: `annotation_store.py`의 `rle_encode()` 내부 dtype 캐스팅 문제로 원인이 명확히 좁혀져 있음(`np.diff(flat_uint8,...)`가 uint8을 유지해 1→0 하강 엣지가 언더플로우). 다른 항목과 파일·모듈 의존관계가 전혀 없어 다른 라운드를 기다릴 이유가 없다.
- **선행 필요성**: R3에서 `annotation_canvas.py`(브러시 도구가 그리는 위젯)를 건드리게 되는데, BUG-002가 먼저 고쳐져 있어야 R3 검증 시 "브러시로 그린 마스크가 저장 후에도 남아있는지" 실제로 확인할 수 있다. R3보다 먼저 고치지 않으면 브러시 관련 검증 자체가 무의미해진다.
- **현재 노출 범위**: `projects/nok/`은 전부 polygon이라 아직 미발현이지만, v1.6.0 초기 릴리즈부터 존재한 결함(QA.md 근거)이므로 브러시 도구를 쓰는 다른/향후 프로젝트에서는 이미 데이터를 잃고 있었을 가능성이 있다 — 조기 수정 압박이 크다.
- **수정 난이도**: 하(下). `flat = (flat != 0).view(np.uint8)` 이후 `np.diff` 이전에 더 넓은 정수형(`int16`/`int8`)으로 캐스팅하거나, `.astype(np.int8)` 후 diff 계산하면 해결된다. 예: `diff = np.diff(flat.astype(np.int8), prepend=np.int8(0), append=np.int8(0))`. 별도 설계 결정 불필요.

## 항목별 상세

### BUG-002 — brush_mask RLE 인코딩 언더플로우
- **해결 방향**: `rle_encode()`에서 `np.diff` 호출 전 `flat`을 부호있는 정수형(`int8` 또는 `int16`)으로 캐스팅. 기존 `n = min(len(starts), len(ends))` 방어 코드는 유지(진짜 경쟁조건 대비).
- **예상 효과**: brush_mask 어노테이션 저장 후 재로드 시 100% 복원(현재 100% 유실). 정량적 회귀 테스트: 100px/170만px 마스크 라운드트립 검증(검증 에이전트가 이미 재현 스크립트 보유).
- **난이도**: 하.
- **리스크**: 낮음 — 순수 버그 수정, 기존 정상 동작(polygon)에는 영향 없음. 단, **이미 저장된 빈 RLE(`"rle": ""`)로 남은 과거 데이터는 이 수정으로 복구되지 않는다** — 원본 마스크 자체가 저장 시점에 이미 소실됐기 때문. 복구 불가능함을 사용자에게 알릴 필요는 있으나 별도 결정 사항은 아님(복구할 데이터가 물리적으로 없음).
- **의존관계**: R3(annotation_canvas 캐시 작업)의 전제조건.

### #2 — 콜드 임포트 지연로딩
- **해결 방향**: `main.py`의 `_preload_libs()`에서 `albumentations`, `torchvision`은 QApplication 생성 전 즉시 로드하지 않고, 실제 필요한 시점(학습 탭 진입, 또는 학습 시작 버튼 클릭)에 지연 임포트. `numpy`, `cv2`, `PIL.Image`, `torch`, `matplotlib`는 기존대로 즉시 로드(다른 탭에서 상시 사용).
- **예상 효과**: 기동 시간 ~3.3초 → 추정 ~0.6초대(albumentations 1.9s + torchvision 0.8s 절감분 대부분). 학습 탭 최초 진입 시에만 지연 발생.
- **난이도**: 중. 단순 이동이 아니라 지연 로딩된 모듈을 참조하는 모든 지점(`app/core/augmentations.py`, `app/core/dataset.py`, `app/core/trainer.py` 등)이 import 시점에 깨지지 않도록 함수 내부 지역 임포트로 바꿔야 함.
- **리스크**: **중~상**. `main.py` 주석에 "일부 환경에서 DLL 로딩 순서·PATH 문제로 나중에 import 하면 에러가 날 수 있어서 QApplication 생성 전에 미리 로드한다"고 명시되어 있고, 이는 과거 `BUG-001`(closed, PyQt6 DLL 로드 실패)과 같은 계열의 Windows/Anaconda DLL 이슈로 추정된다. torchvision을 지연 로딩하면 동일한 클래스의 DLL 순서 문제가 재발할 가능성이 있음 — **사용자 결정 필요**(decisions-needed.md 등록).
- **의존관계**: 없음. 다른 라운드와 독립.

### #3 — 학습 데이터로더 캐시 + num_workers
- **해결 방향**:
  1. `SegmentationDataset.__getitem__`이 매 패치마다 `Image.open(img_path)`를 새로 여는 구조 개선 — 같은 이미지에서 연속으로 패치를 뽑는 `random_crop` 모드에 한해 마지막으로 연 이미지(디코딩 결과)를 1~2장 캐시(LRU)해 재사용. `patches_per_image=50`이면 이미지당 디코딩 50회 → 캐시 히트 시 1회로 축소 가능.
  2. `config_form.py`의 `num_workers` 기본값을 0에서 상향 조정해 배치 로딩을 GPU 스텝과 오버랩. `main.py`에 이미 `if __name__ == "__main__":` 가드가 있어 Windows spawn 방식 멀티프로세싱 자체는 가능하나, `Dataset`이 들고 있는 `augment_fn`(Albumentations Compose)이 각 워커 프로세스로 pickle되어야 함 — 실제로 pickle 가능한지 사전 확인 필요.
- **예상 효과**: 배치 로딩 505ms → (캐시 히트 시) 대폭 감소 + num_workers>0이면 GPU 스텝(165ms)과 오버랩되어 이론상 학습 처리량 3~8배 개선(검증 로그 추정치).
- **난이도**: 상. Dataset 캐시는 `random_crop`의 인덱스 순회 순서(현재 `idx % len(pairs)`로 이미지가 흩어져 반복됨)와 맞물려 캐시 적중률을 보장하려면 샘플링 순서 조정이 함께 필요할 수 있음. num_workers 변경은 멀티프로세싱 안정성 검증이 필요.
- **리스크**: 중~상. (a) DataLoader 워커 프로세스에서 예외 발생 시 에러 메시지가 불명확해질 수 있음 — `TrainerWorker.training_error` 시그널 경로 유지 확인 필요. (b) 캐시가 이미지를 들고 있는 상태에서 라벨링 탭과 동시에 같은 프로젝트 이미지를 수정하면 stale 캐시 가능성(단, 학습 중에는 통상 라벨링 탭 미사용이므로 영향 작음). (c) num_workers 기본값 상향은 저사양 PC에서 오히려 역효과 가능 — **사용자 결정 필요**(decisions-needed.md 등록: 기본값 몇으로 할지).
- **의존관계**: 없음(BUG-002/R3와 파일 안 겹침). 다만 리스크가 가장 커서 독립 라운드로 격리.

### #4 — annotation_canvas 이미지 캐시
- **해결 방향**: `load_image()`에서 `QPixmap(str(path))` 결과를 LRU 캐시(최근 1~2장)로 유지 — 재방문 시 재디코딩 생략. 추가로 다음/이전 이미지 프리페치(백그라운드 스레드)는 선택 사항으로 별도 검토(범위 확대 리스크 있어 이번 라운드는 캐시만).
- **예상 효과**: 재방문 시 70~95ms → 거의 0ms. 5장 연속 전환 366ms → 첫 방문 이후 캐시 히트 구간 대폭 단축. 순방향으로만 계속 넘기는 워크플로우(한 번씩만 봄)에서는 효과 제한적 — 실사용 패턴(되돌아가기 빈도)에 따라 체감 차이.
- **난이도**: 중. 기존 `_pixmap`, `_display_pixmap`, `_display_pixmap_key`, `_pixel_image` 등 이미지별 파생 상태가 여러 개 있어 캐시 키에 이 모두를 함께 묶어야 함(단순 QPixmap만 캐시하면 나머지 파생 상태 재계산 비용은 그대로 남음).
- **리스크**: 낮음~중. 메모리 사용량 증가(검증 로그: 이미지 1장당 QPixmap+PIL 동시 보유 시 RSS ~152MB/장 — 2장 캐시면 +150MB 안팎, 대형 원본 이미지 프로젝트에서 유의). 캐시 무효화(이미지 파일 외부에서 교체된 경우) 처리 필요.
- **의존관계**: 같은 파일(#7)과 R3로 묶음.

### #5 — 추론 결과 컬러화/블렌딩 다운스케일
- **해결 방향**: `_colorize_and_blend()`가 원본 해상도(5472×3648) 그대로 컬러화하는 대신, 화면 표시용으로는 `annotation_canvas.py`가 이미 쓰고 있는 `_MAX_OVERLAY_DIM = 2048` 같은 상한을 적용해 다운스케일 후 컬러화/블렌딩 — 결과 저장(내보내기) 시에는 원본 해상도 유지 옵션 분리 검토.
- **예상 효과**: 992ms/회 → 해상도 축소 비율(면적 기준 약 1/7)에 비례해 대폭 감소, 대략 150ms대 예상(정성적 추정, 실측 필요).
- **난이도**: 중. 화면 표시 경로와 "결과 저장" 경로를 분리해야 화질 저하 없이 저장이 가능 — 현재 `_colorize_and_blend()`가 두 경로에 공용으로 쓰이는지 확인 필요(구현 시 파악).
- **리스크**: 중. 화면 미리보기 해상도를 낮추면 결함 검수 시 미세한 경계 오차를 놓칠 가능성 — **사용자 결정 필요**(decisions-needed.md 등록: 상한 픽셀 값, 저장 시에도 다운스케일 적용할지).
- **의존관계**: 없음.

### #6 — image_browser 검색 디바운스 + 캐시
- **해결 방향**: `_on_search_changed`에 `QTimer.singleShot` 기반 디바운스(예: 150~250ms, `annotation_canvas.py`의 `_cache_pixel_image` 지연 패턴과 동일 관용구 재사용) 적용 + `get_label_status()` 결과를 이미지 목록 reload 시점에 한 번만 계산해 캐시, 검색/정렬 시에는 캐시된 상태만 필터링(트리 전체 rebuild 대신 필요한 최소 갱신 검토).
- **예상 효과**: 정적 추정 — nok(5장)에서는 keystroke당 5ms(무의미)지만 수백~수천 장 프로젝트에서는 선형 비례이므로 체감 개선 클 것으로 예상. **정량적 수치는 미확보** (아래 불확실성 절 참고).
- **난이도**: 하~중. 디바운스는 하, 상태 캐시는 이미지 추가/삭제/라벨 저장 시 무효화 로직이 필요해 중.
- **리스크**: 낮음. 디바운스는 표준 패턴이라 회귀 가능성 작음. 캐시 무효화 누락 시 "라벨 상태 아이콘이 갱신 안 됨" 류의 UI 버그 가능성 — 캐시 무효화 트리거(라벨 저장, OK 토글, 이미지 추가/삭제) 목록을 구현 시 빠짐없이 확인 필요.
- **의존관계**: 없음. #8과 파일은 다르지만 둘 다 저리스크 JSON I/O 최적화라 R6로 묶음.

### #7 — bbox fallback 전체 스캔
- **해결 방향**: `_resolve_overlap_and_merge._has_pixels`의 fallback 경로에서 20MP 전체 `mask.any()` 대신, 이미 계산되어 있는 bbox 범위만 우선 스캔하고 그래도 안 되면 원본 배열 대신 다운샘플된 버전으로 근사 체크 후 필요한 경우에만 전체 스캔.
- **예상 효과**: 드문 케이스(43ms 스파이크)의 빈도/크기 축소. 이미 대부분 최적화되어 있어 전체 체감 효과는 작음(검증 로그도 "영향 작음"으로 평가).
- **난이도**: 하.
- **리스크**: 낮음. fallback 경로 자체가 드물게만 실행되므로 회귀 영향 범위 작음.
- **의존관계**: #4와 같은 파일(annotation_canvas.py) — R3로 묶어 한 번에 검증.

### #8 — auto_labeler JSON 중복 read
- **해결 방향**: `collect_unlabeled()`에서 `get_ok(p)`와 `load(p)`가 각각 JSON을 여는 대신, `get_label_status()`(다른 곳에서 이미 쓰는 통합 조회 함수로 추정, 구현 시 실제 시그니처 확인) 하나로 통합해 1회 read로 축소.
- **예상 효과**: 정적 추정 — 오토라벨 대상 수집은 1회성 동작이라 체감 영향 미미. 이미지 수가 많을수록 절대 시간은 늘지만 우선순위 P3.
- **난이도**: 하.
- **리스크**: 낮음. 단순 리팩터.
- **의존관계**: 없음. R6로 묶음(저비용 항목끼리 한 라운드에 처리해 검증 비용 절감).

## 불확실성 — #6, #8 (정적 분석만, nok 5장으로는 미실측)

검증 로그가 명시: nok 프로젝트는 이미지 5장뿐이라 #6(검색 디바운스)과 #8(중복 read)의 실제 스케일 영향은 실측되지 않았고, 코드 흐름 분석만으로 "이미지 수에 선형 비례할 것"이라 추정한 상태다.

- 이번 계획에서는 **구현을 막지 않는다**: 두 항목 모두 수정 비용이 낮고(디바운스는 표준 패턴, dedupe read는 단순 리팩터) 실패 시 리스크도 낮아, 실측 없이 진행해도 하방 리스크가 작다고 판단했다.
- 다만 **개선 효과 자체는 R6 검증 단계에서 재확인 조건을 건다**: nok(5장)로는 개선을 증명할 수 없으므로, 검증 에이전트가 R6 검증 시 더미 이미지 수백~수천 장 규모의 합성 프로젝트(예: 빈 파일 500장 + 라벨 상태가 섞인 JSON)를 만들어 디바운스 적용 전/후 keystroke당 처리 시간, `collect_unlabeled()` 호출 시간을 실측하도록 명시한다. 실측 결과 개선 폭이 미미하면 QA.md/roadmap.md에 "정적 추정과 실측 불일치"로 기록하고 우선순위를 재검토한다.

## 트레이드오프 결정 (2026-08-19, 사용자 확인 완료)

`docs/decisions-needed.md`에 등록했던 3건 모두 사용자 확인 완료 — 해당 항목 삭제, 결과만 기록:

1. **#2** — 리스크 감수하고 지연 임포트 적용. DLL 순서 문제 재발 시 롤백. R2 구현 시 `main.py`의
   `_preload_libs()`에서 albumentations/torchvision을 지연 임포트로 전환하고, 검증 단계에서
   깨끗한 환경(가능하면 다른 Windows/Anaconda 조합)에서 기동 확인을 반드시 포함할 것.
2. **#3** — `num_workers` 기본값을 **자동 감지(CPU 코어 수 기반)**로 설정. 구현 시
   `os.cpu_count()` 기반으로 합리적 상한(예: `min(4, cpu_count - 1)` 등 구체값은 구현 단계에서
   확정)을 두고, 사용자가 여전히 UI에서 수동 override 가능하도록 유지.
3. **#5** — **화면 미리보기만** `_MAX_OVERLAY_DIM=2048` 상한 적용, **저장/내보내기 결과는 원본
   해상도 유지**. 화면 표시 경로와 저장 경로를 분리하는 구현이 필수 조건.
