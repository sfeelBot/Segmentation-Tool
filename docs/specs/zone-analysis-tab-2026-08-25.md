# 존(Zone) 분석 탭 — 배터리 캡 녹 검사 도구 스펙

접수일: 2026-08-25. 브랜치 `feature/zone-analysis-tab`. 기존 4탭(모델/라벨링/학습/추론)과
완전히 독립된 신규 도구. 이번 문서는 기획 산출물 — 코드 변경 없음.

> **2026-08-25 수정**: 사용자가 참고 이미지(배터리 캡 사진 위 빨간 라인 오버레이)로
> 직접 정정함 — 빨간 라인은 완벽한 수학적 원이 아니라 **실제 크림핑/가스켓 링 에지를
> 따라가는 울퉁불퉁한 폐곡선(컨투어)**이다. 원래 요청 문구 "동심원 형태의 엣지 여러개"를
> "완벽한 원"으로 잘못 해석해 판단 2를 `(cx, cy, r)` 파라메트릭 원 모델로 설계했던 것은
> 오판 — **에지를 따라가는 컨투어(폐곡선) 기반**으로 전면 수정. 이 수정 이후 문서 전체에서
> "원"이라는 표현은 원칙적으로 "경계(컨투어)"로 교체했고, "동심원 구조"는 배터리 캡의
> **물리적 형상을 설명하는 도메인 용어**로만 남겨둔다(수학적 원을 뜻하지 않음). 판단 1·3·4는
> 이번 수정과 무관해 그대로 유지.

## 배경

사용자가 준 실제 검사 대상 예시: 삼성SDI 원통형 배터리 캡 상단 이미지(BMP, 5472×3648,
20MP, acA5472-17uc + 50mm 렌즈), "돔"/"돔+동축" 조명 쌍. 배터리 캡은 동심원 구조 —
바깥 케이스 테두리 → 크림핑(가스켓) 시일 링 → 안쪽 캡 디스크(QR 2개) 순서로 여러 경계가
있고, 크림핑/가스켓 링 부근에 금색/황갈색 변색(녹 의심)이 육안으로도 보임. 사용자가 준
참고 이미지를 보면 이 경계들은 제조 공차·촬영 각도 등으로 **완전한 원이 아니라 실측 에지를
그대로 따라가는 울퉁불퉁한 폐곡선**이다(사용자 표현: "각 3개의 원이 아니고 영역별 contour내부의
원형"). "영역별 퍼센테이지"는 이 경계들 사이 고리(annulus) 구역별 녹 검출 면적 비율.

## 확정된 요구사항 (사용자 답변 완료 — 재질문 불필요)

1. 완전 독립 도구 — `app/core/project.py`의 프로젝트 시스템(images/annotations/
   checkpoints/user_models) 미사용. 이미지 파일 직접 열기 + 기존 학습된 체크포인트(.pt)
   직접 로드 + 그 자리에서 추론.
2. 동심원 형태의 경계 검출 — 자동(에지 검출 + 컨투어 추출 기반, 아래 판단 2 참고) +
   수동(점 추가/드래그/삭제로 경계 폴리곤 생성·조정·삭제) 둘 다 지원, 여러 개의 경계 정의
   가능. **2026-08-25 정정**: 원래 "동심원 엣지"라는 표현을 완벽한 수학적 원(Hough Circle)
   으로 오판했던 것을 사용자가 직접 정정 — 실제로는 각 경계가 육안으로는 원처럼 보이지만
   실측하면 완전한 원이 아닌 폐곡선(컨투어)이므로, 검출·저장·편집·존 계산 전부 컨투어
   기반으로 재설계함(아래 판단 2).
3. 존 선택 + 퍼센티지 — 인접한 두 경계 사이(또는 최내부/최외부) 구역을 클릭 선택 →
   그 구역 내 "녹" 클래스 마스크 면적 비율(%) 표시.
4. 블랍 삭제 — 추론 마스크의 오검출 connected component를 클릭으로 선택해 삭제,
   삭제 후 존별 퍼센티지 재계산.
5. 브랜치 `feature/zone-analysis-tab`, main 병합 여부는 추후 사용자 확인(이번 라운드
   범위 아님).

## 판단 2 — 경계(Contour) 데이터 모델: 폐곡선 점 목록, 면적 기준 정렬

**2026-08-25 전면 수정**: 애초 요구사항 문구("동심원 형태의 엣지 여러개")를 리더가
"완벽한 원"으로 오판해 `(id, cx, cy, r)` 파라메트릭 원으로 설계했던 것을 사용자가 직접
정정. 실측 이미지의 크림핑/가스켓 링 에지는 완전한 원이 아니므로(제조 공차, 촬영 각도 등),
아래와 같이 폐곡선(컨투어) 기반으로 재설계한다.

**결론: 각 경계를 `Contour(id, points: list[tuple[float, float]])`로 저장한다.**
`points`는 이미지 좌표계의 폐곡선 정점 목록(첫 점=마지막 점 중복 저장하지 않음, 렌더링/
연산 시 암묵적으로 닫힌 것으로 취급 — `annotation_canvas.py`의 폴리곤 어노테이션과 동일
관례). 원(circle) 전용 필드(`cx`, `cy`, `r`)는 전부 제거.

- **순서 개념(바깥→안쪽)**: 반지름 대신 **면적 기준 내림차순 정렬**로 유지한다 —
  `cv2.contourArea(points)` 계산값이 클수록 바깥쪽. 원이 아니어도 "이 폐곡선이 저 폐곡선을
  포함하는가"의 근사치로 면적 비교가 안정적으로 동작한다(실제 배터리 캡 구조상 경계들이
  대략 nested이므로 원래 판단 2의 "반지름 오름차순 정렬"과 동일한 역할을 면적이 대신함).
- **존(zone) 계산도 원판(disk) 대신 폴리곤 채움 마스크의 집합 차집합**으로 재정의한다 —
  자세한 연산은 아래 "존 계산 로직" 절 참고. 공유 중심점을 강제하지 않는다는 원래 취지
  (실측 오차에 견고해야 한다는 것)는 폐곡선 기반에서 더 자연스럽게 성립한다 — 애초에
  "중심"이라는 개념 자체가 폐곡선에는 없고, 마스크 차집합 연산은 두 폐곡선이 완벽히
  동심이 아니어도(경계가 울퉁불퉁해도) 그대로 성립한다.
- OpenCV `cv2.findContours()`도 원래 각 컨투어를 점 목록(`ndarray of (x,y)`)으로 반환하므로,
  자동검출 결과를 변환 없이(또는 `approxPolyDP`로 점 개수만 줄여서) 그대로 저장 형식으로
  쓸 수 있다는 부수 이점이 있음 — 판단 2 원안의 "Hough 결과와 형식이 일치한다"는 이점이
  컨투어 기반에서도 동일하게 성립(도구만 `HoughCircles`→`findContours`로 바뀜).
- UX 상 사용자에게는 여전히 "동심원 편집"으로 보이게(면적 내림차순 자동 정렬 표시,
  자동검출 결과가 실제 물리적 링 위치에 자연히 잡힘) — 데이터 모델과 사용자 멘탈 모델을
  분리하는 원래 판단 2의 취지는 그대로 유지, 실현 수단만 원→폐곡선으로 교체.

## 판단 3 — 체크포인트→모델 재구성 (요구사항 1의 핵심 제약)

`app/core/inference_engine.py` 조사 결과:

- `load_model_from_ckpt(ckpt_path)` — 체크포인트의 `config.model_source`가
  `"preset:<key>"`로 시작하면 **완전히 독립적으로**(프로젝트/모델탭 상태 참조 없음)
  `app.model_presets` + `app.core.model_loader.load_from_code()`로 모델을 fresh
  weights로 인스턴스화한 뒤 `load_state_dict()`로 채운다 — **그대로 재사용 가능**.
- 단, `model_source == "loaded"`(모델 탭에서 사용자가 직접 붙여넣은 커스텀 아키텍처)인
  경우 `load_model_from_ckpt()`는 `None`을 반환한다. 이유: 체크포인트에는 소스 코드가
  저장되지 않고 태그 문자열만 있음(2026-08-20 기획 로그에서 이미 확인된 사실). 기존
  `inference_tab.py`는 이 경우 `win._model_tab.loaded_model`(같은 세션의 모델 탭 인메모리
  상태)로 폴백하는데, **이는 정확히 이번 도구가 배제해야 할 탭 간 교차 의존**이다.
- **대응**: 체크포인트 선택 시 `load_checkpoint_meta()`로 `model_source`를 먼저 읽는다.
  - `preset:*` → 자동 인스턴스화(추가 UI 없음).
  - 그 외("loaded" 또는 구형 체크포인트로 정보 없음) → 탭 안에 모델 코드 입력 박스를
    노출하고, 모델 탭과 동일한 두 단계(Validate → Load)로 `app/core/model_validator.py`의
    `validate(code)` + `app/core/model_loader.py`의 `load_from_code(code)`를 **그대로**
    호출한다. 둘 다 Qt/프로젝트 의존성 없는 순수 함수라 이식에 문제없음. 단
    `model_loader.save_user_code()`는 프로젝트의 `user_models_dir()`에 파일을 쓰므로
    **호출하지 않는다**(붙여넣은 코드는 세션 동안만 메모리에 유지, 디스크에 저장하지
    않음 — 독립성 유지).

## 판단 4 — 타겟(녹) 클래스 정의: 프로젝트 `classes.json` 미사용

`inference_engine.run()`은 내부에서 무조건 `annotation_store.load_classes()`를 호출하는데,
이는 `_project.classes_file()`(현재 열려 있는 프로젝트의 `classes.json`)을 읽는다. 이 신규
탭이 살아있는 동안 `MainWindow`에는 항상 어떤 프로젝트든 열려 있으므로(`main.py`가
프로젝트 선택 후에만 `MainWindow`를 생성) `_project.current()`가 `None`이 되는 경우는
실제로는 없지만, **그 프로젝트의 클래스 정의가 지금 로드한(어디서 왔는지 모르는) 체크포인트와
아무 관계가 없을 수 있다** — 이름/색상이 틀리게 표시될 실질적 정확성 위험이 있음(단순한
"독립성 원칙 위반" 수준이 아니라 실사용 버그).

**대응(최소 침습)**: `inference_engine.run()` / `run_sliding_window()` / `refilter()`에
`classes: list[ClassDef] | None = None` 선택 인자를 추가한다(3곳 각 1~2줄). `None`이면
기존과 동일하게 `load_classes()` 폴백 — **기존 4탭 호출부는 인자를 안 넘기므로 동작
변화 없음(회귀 위험 없음)**. 신규 탭은 항상 이 인자를 명시적으로 채워서 넘긴다.

이 탭에서 `classes` 리스트를 만드는 방법은 프로젝트 파일을 읽지 않고, **추론 1회 실행 후
반환된 `raw_class_map`의 고유값(배경 0 제외)으로부터 즉석 구성**한다 — 클래스 이름/색상을
사용자가 미리 입력할 필요가 없다:
- `raw_class_map`에 등장하는 배경 아님 클래스 id가 1개뿐이면 자동으로 그 id를 "타겟(녹)"으로
  선택하고 기본 이름 "class_1"(수정 가능한 텍스트 필드 제공, 자유 표기 "녹" 등)을 부여.
- 2개 이상이면 드롭다운으로 사용자가 타겟 id를 고른다(v1 범위는 아래 "결정 필요" 참고).
- 색상은 기존 `annotation_store.DEFAULT_PALETTE`(프로젝트 의존 없는 모듈 레벨 상수)를
  그대로 재사용해 `class_id`로 인덱싱 — 새 팔레트 발명 없음.

체크포인트에 클래스 메타데이터 자체를 저장하는 근본 해결(=`app/core/trainer.py`가
`config["classes"]`도 함께 저장)은 `trainer.py`(공유 파일, 기존 4탭 학습 플로우에 영향)를
건드려야 하는 별개 스코프라 **이번 기능 범위 밖으로 명시적으로 제외**한다. 향후 후보로만
기록(아래 "향후 확장 후보").

## 데이터 흐름

```
1. 이미지 로드(QFileDialog, 프로젝트 밖 임의 경로)
2. 체크포인트 로드(QFileDialog, *.pt)
   → load_checkpoint_meta()로 model_source 확인
   → preset: 자동 인스턴스화 / 그 외: 모델 코드 붙여넣기(Validate→Load)
3. 추론 실행 (engine.run 재사용, classes=None으로 1차 실행해 raw_class_map 확보
   → 고유 클래스 id로 즉석 ClassDef 구성 → 필요시 engine.refilter로 classes 반영해 재컬러화)
4. 동심원 형태의 경계 정의
   4a. 자동 검출(Canny+findContours+원형도/면적 필터) — 원본을 다운스케일(기존
       _MAX_OVERLAY_DIM=2048 관례 재사용)해 검출 후 점 좌표를 원본 스케일로 역산
   4b. 수동 편집 — 자동검출 폴리곤의 점 드래그 이동/삽입/삭제, 또는 빈 곳에서 클릭으로
       점을 찍어 새 폐곡선을 처음부터 그리기
5. 존별 마스크 계산 (zone_metrics.zones_from_contours)
6. 존 선택 → 해당 존 마스크 AND 타겟 클래스 마스크 → 퍼센티지 표시
7. (선택) 블랍 클릭 삭제 → 타겟 마스크에서 해당 connected component 제거 → 6 재계산
```

3~7단계는 전부 numpy/cv2 배열 연산이라 재계산 비용이 낮음(5472×3648 기준, 다운스케일
없이도 500ms 미만대 예상 — 실측은 구현/검증 단계에서 확인).

## UX 흐름 상세

### 경계(컨투어) 검출/편집

- "자동 검출" 버튼 + 민감도 슬라이더 1개(내부적으로 Canny 임계값 매핑) — v1은 파라미터
  노출을 최소화(라더: 필요해지면 그때 추가). 정확한 매핑값은 아래 "라운드 분할" 라운드 2의
  스크립트 프로토타입 결과로 확정.
- 검출 결과는 캔버스 위에 반투명 폴리곤 외곽선 + 각 정점 마커(원형 핸들)로 표시 —
  `annotation_canvas.py`의 `_draw_wip_polygon()` 정점 렌더링 스타일(작은 원 마커) 재사용.
- 수동 편집(신규 구현, 위 "파일 구조 제안" 참고):
  - 기존 정점 위 드래그 → 그 정점만 이동.
  - 변(edge) 중간 지점 근처 클릭 → 새 정점 삽입.
  - 정점 선택 후 Delete 키 또는 우클릭 메뉴 → 정점 삭제(정점 3개 미만이 되면 폐곡선
    자체를 삭제 확인).
  - 캔버스 빈 곳에서 순차 클릭 → 새 폐곡선을 처음부터 그리기(annotation_canvas.py의
    "클릭으로 점 추가 + 첫 점 근처 스냅으로 닫기" 패턴 그대로 차용), Delete/우클릭 메뉴로
    폐곡선 전체 삭제.
- 경계 목록은 면적 내림차순으로 자동 정렬해 사이드 패널에 표시(중심부→바깥쪽 순).

### 존 선택 및 네이밍

- 존 개수 = 경계 개수 + 1 (중심부 1 + 경계 사이 고리 (N-1) + 바깥쪽 1, 경계가 1개뿐이면
  중심부/바깥쪽 2개) — 판단 2의 면적 내림차순 정렬 기준.
- 네이밍 제안: `중심부`(면적 최소 경계 내부), `링 1`, `링 2`, …, `링 N-1`(면적 기준
  인접 경계 사이), `바깥쪽`(면적 최대 경계 밖, 이미지 경계까지).
- 캔버스에서 존 클릭 또는 사이드 리스트에서 존 클릭 → 해당 존 하이라이트 + 퍼센티지 표시.
  리스트는 항상 전체 존의 퍼센티지를 한번에 보여주고(요구사항이 "클릭 등으로 선택"이라
  구체 인터랙션을 정했으므로), 클릭은 캔버스 하이라이트 포커스 이동 용도로 둔다.

### 존 계산 로직 (신규 절 — 마스크 집합 연산)

두 인접 경계 각각을 이진 마스크로 채운 뒤 차집합을 구한다:

1. `mask_i = np.zeros(img_shape, uint8)`; `cv2.fillPoly(mask_i, [points_i], 1)`
   (또는 `cv2.drawContours(mask_i, [points_i], -1, 1, thickness=-1)` — 동일 결과, 팀
   관례상 `fillPoly` 채택. 둘 다 `cv2` 표준 함수라 신규 의존성 없음).
2. 경계를 면적 내림차순 `[C_0(최대), C_1, …, C_{N-1}(최소)]`로 정렬했을 때:
   - `Zone_center = mask(C_{N-1})` (최소 경계 내부 자체가 하나의 존).
   - `Zone_i = mask(C_i) AND NOT mask(C_{i+1})` for `i = 0 .. N-2` (바깥쪽 경계 마스크에서
     안쪽 경계 마스크를 뺀 고리형 존 — 두 경계가 완벽히 nested라는 전제 하에 XOR과 동일하지만
     안전하게 `AND NOT`으로 계산, nested가 아닌 예외 입력에도 음수 없이 안전).
   - `Zone_outside = 전체 이미지 마스크 AND NOT mask(C_0)` (최대 경계 밖, 이미지 경계까지
     — 판단 2/3에서 확정된 것과 동일하게 기본 포함).
3. 각 `Zone_k` 마스크와 타겟 클래스 이진 마스크를 AND한 뒤 픽셀 카운트 비율로 퍼센티지 산출
   (기존 판단 4의 즉석 클래스 구성과 동일 소스).
4. **전제 조건 명시**: 이 연산은 경계들이 대략 nested(바깥 경계가 안쪽 경계를 완전히
   포함)라는 것을 전제로 한다 — 배터리 캡의 실제 물리 구조상 항상 성립. 만약 사용자가
   수동 편집으로 경계를 서로 교차하게 만들면(비정상 입력) `Zone_i`가 예상과 다른 모양이
   될 수 있으나 이는 입력 데이터 오류이지 연산 자체의 결함이 아님 — v1에서는 별도
   경고/방지 로직을 추가하지 않는다(발생 가능성 낮고, 방지하려면 복잡한 기하 검증이
   필요해 YAGNI).

### 블랍 삭제

- 타겟 클래스 이진 마스크에 `cv2.connectedComponentsWithStats(mask, connectivity=8)`로
  라벨맵 생성(기존 `inference_engine._compute_blobs_and_filter()`와 동일 API, 다만 이
  탭은 단일 이진 마스크 + 클릭 삭제 전용이라 별도의 작은 헬퍼로 둠 — confidence/size
  threshold 필터링 로직까지 그대로 가져오면 이 도구엔 불필요한 결합이 생김).
- 캔버스 클릭 → 화면 좌표를 이미지 좌표로 역변환(줌/팬 반영, `overlay_viewer.py`의
  `mc`→`mi` 변환 공식 재사용) → 라벨맵에서 해당 좌표 라벨 조회 → 배경(0)이 아니면 삭제
  대상 집합에 id 추가 → 표시 마스크에서 `np.isin(labels, removed_ids)` 위치를 배경 처리
  → 존 퍼센티지 재계산 트리거.
- 삭제 취소(Undo) 1단계는 있으면 좋지만 v1 필수 아님(라벨링 탭처럼 무한 undo 스택까지는
  과함 — 필요성이 확인되면 후속 라운드에서 검토).

## 리스크 / 주의사항

- 5472×3648(20MP) BMP 이미지 — 기존 관례(`_MAX_OVERLAY_DIM=2048`)를 그대로 따라 화면
  표시/컨투어 검출용 다운스케일과 저장/계산용 원본 해상도를 분리 유지해야 함(기존
  `inference_engine.py`/`annotation_canvas.py`가 이미 이 패턴을 쓰고 있어 신규 코드도
  동일 관례 적용).
- Canny+findContours는 Hough 대비 파라미터(임계값·원형도·면적 필터)에 더 민감할 수 있음
  — 라운드 2a 스크립트 프로토타입에서 실제 예시 이미지로 먼저 검증(위 라운드 분할 참고).
- 존 계산(마스크 차집합)은 경계들이 대략 nested라는 전제 — 배터리 캡 실제 구조상 항상
  성립하지만, 수동 편집으로 비정상 교차 입력을 만들면 결과가 왜곡될 수 있음(v1은 방지
  로직 없음, "존 계산 로직" 절 참고).
- `inference_engine.py`는 기존 4탭이 공유하는 파일 — `classes` 옵션 인자 추가가 기존
  호출부(`inference_tab.py`)에 회귀를 일으키지 않는지 검증 단계에서 반드시 확인.
- 커스텀 모델 코드 입력 경로는 `model_validator.py`/`model_loader.py`의 기존 샌드박스
  정책(`docs/SECURITY.md`)을 그대로 따름 — 신규 우회 경로를 만들지 않음.
