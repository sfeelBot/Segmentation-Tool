> 계산이 왜곡된다 — 참고 이미지의 빨간 라인도 다시 보면 "에지를 있는 그대로 따라가는
> 자유곡선"이 아니라 **"실제 픽셀 위치에 최대한 딱 맞는 원"**이었다는 것으로 최종 확정.
> **결론: 데이터 모델은 다시 `(id, cx, cy, r)` 파라메트릭 원으로 되돌린다.** 단, 검출
> 파이프라인은 1차 수정 이전(Hough 단독)으로 그냥 되돌리지 않고, 1차 수정에서 조사한
> Canny+findContours 흐름 뒤에 **강건한(outlier-resistant) 원 피팅 단계를 추가**하는
> 형태로 합친다(아래 판단 2 최종본). 이 2차 수정 이후 문서 전체에서 "원(circle)"이 다시
> 정본 용어이고, "경계(컨투어)"는 검출 파이프라인 중간 산출물(원 피팅 입력)을 가리킬
> 때만 쓴다. 판단 1·3·4, 블랍 삭제(라운드 4)는 1차·2차 수정 모두와 무관해 손대지 않음.

## 배경

사용자가 준 실제 검사 대상 예시: 삼성SDI 원통형 배터리 캡 상단 이미지(BMP, 5472×3648,
20MP, acA5472-17uc + 50mm 렌즈), "돔"/"돔+동축" 조명 쌍. 배터리 캡은 동심원 구조 —
바깥 케이스 테두리 → 크림핑(가스켓) 시일 링 → 안쪽 캡 디스크(QR 2개) 순서로 여러 원형
경계가 있고, 크림핑/가스켓 링 부근에 금색/황갈색 변색(녹 의심)이 육안으로도 보임.
**실제 형상 자체는 원**이지만, 녹(불량)이 에지 근처 픽셀을 침범하면 순수 에지 추출
결과가 그 방향으로 튀어나오게 잡힐 수 있어(제조 공차·촬영 각도로 인한 미세 왜곡과는
별개로, 불량 자체가 만드는 에지 왜곡) 검출된 경계가 실제 원형에서 벗어나면 안 된다 —
사용자 확정 표현: "자동 검출하더라도 원형을 유지해줘. 불량 때문에 이상하게 잡으면
안되니까". 따라서 최종 저장 형식은 원(circle)이되, 검출 과정에서 이런 국소적 왜곡(이상치)에
강건해야 한다(아래 판단 2). "영역별 퍼센테이지"는 이 원형 경계들 사이 고리(annulus)
구역별 녹 검출 면적 비율.

## 판단 2 — 원(Circle) 데이터 모델 + 컨투어 기반 검출 파이프라인에 강건한 원 피팅 결합 (최종)

**2026-08-25 2차 수정(최종, 1차 수정을 다시 뒤집음)**: 1차 수정에서 저장 형식을 폐곡선
점 목록 `Contour(id, points)`로 바꿨던 것을 사용자가 재정정 — 참고 이미지의 빨간 라인은
"에지를 있는 그대로 따라가는 자유곡선"이 아니라 "실제 픽셀 위치에 최대한 딱 맞는 원"이
의도였고, 자동 검출이 순수 컨투어를 그대로 쓰면 녹(불량)이 침범한 에지 방향으로 경계가
찌그러질 위험이 있어 명시적으로 원형을 강제해야 함(사용자 표현: "자동 검출하더라도
원형을 유지해줘. 불량 때문에 이상하게 잡으면 안되니까").

**결론: 각 경계를 다시 `Circle(id, cx, cy, r)`로 저장한다.** `Contour(id, points)`는
폐기 — 원(circle) 전용 필드로 되돌림. 다만 1차 수정에서 조사한 컨투어 기반 검출 흐름은
버리지 않고, **검출 파이프라인의 중간 단계로 유지한 뒤 마지막에 원 피팅을 추가**하는
형태로 합친다:

1. `cv2.Canny` 엣지 검출 → `cv2.findContours(RETR_LIST)`로 폐곡선 후보 추출 (1차 수정과
   동일, 그대로 유지).
2. 원형도(`4π·area/perimeter²`)+면적 필터로 링 후보 컨투어 선별 (1차 수정과 동일, 그대로
   유지).
3. **신규 — 원 피팅(이상치에 강건)**: 선별된 컨투어의 점들에 원을 피팅해 최종 `(cx, cy, r)`을
   구한다. `cv2.minEnclosingCircle`은 단일 이상치(녹이 튀어나온 부분 등)에도 반지름이
   과도하게 커질 수 있어 부적합 — 대신 **대수적 최소자승 원피팅(Kasa method)**을 쓴다.
   각 점 `(x, y)`에 대해 `x² + y² = D·x + E·y + F` 로 선형화(`D=2cx`, `E=2cy`,
   `F=r²-cx²-cy²`)한 뒤 `numpy.linalg.lstsq`로 `D, E, F`를 구하고 `cx=D/2, cy=E/2,
   r=√(F+cx²+cy²)`로 환산 — `scipy` 없이 `numpy`만으로 충분(과공학 금지). 1차 피팅 후
   각 점의 잔차(`|dist(point, center) - r|`)가 큰 점(예: 상위 일부 또는 임계값 초과)을
   제외하고 **1~2회만 재피팅**하는 단순 반복으로 이상치(불량 튀어나온 부분)를 걸러낸다
   — 이 이상 정교한 RANSAC 라이브러리 도입은 불필요(YAGNI).
4. 결과는 다시 독립된 `(cx, cy, r)` 원 목록.

- **순서 개념(바깥→안쪽)**: 원으로 되돌아왔으므로 **반지름 오름차순 정렬**로 복귀
  (1차 수정에서 썼던 면적 기준 정렬은 폐기 — 원은 반지름 하나로 바로 비교 가능해 더 단순).
- **존(zone) 계산도 원판(disk) 마스크의 집합 차집합**으로 복귀 — 폴리곤 `fillPoly` 대신
  원 방정식(`(x-cx)²+(y-cy)² ≤ r²` 벡터화 비교, 또는 `cv2.circle(mask, ..., thickness=-1)`)
  으로 마스크를 채운다(자세한 연산은 아래 "존 계산 로직" 절 참고) — 원 데이터가 이미 있으므로
  폴리곤 채우기보다 원 방정식 쪽이 더 단순하고 빠름(라더 3~4단계: 이미 있는 방정식이
  `fillPoly`보다 쉬움).
- OpenCV `cv2.findContours()` + 원 피팅 조합은 `HoughCircles`가 원래 반환하던
  `(x, y, radius)` triple과 최종 형식이 동일해, 저장 스키마·존 계산 로직은 판단 2 원안
  (Hough 단독)과 완전히 같은 인터페이스를 유지한다 — 바뀌는 것은 **검출 내부 구현**뿐
  (Hough 단독 → Canny+findContours+원형도필터+강건한 원피팅), 이 도구를 쓰는 나머지 코드
  (`zone_metrics.py`, `zone_canvas.py`)는 원 모델을 그대로 다루므로 영향 없음.

## 판단 3 — 체크포인트→모델 재구성 (요구사항 1의 핵심 제약)

`app/core/inference_engine.py` 조사 결과:

- `load_model_from_ckpt(ckpt_path)` — 체크포인트의 `config.model_source`가
  `"preset:<key>"`로 시작하면 **완전히 독립적으로**(프로젝트/모델탭 상태 참조 없음)
  `app.model_presets` + `app.core.model_loader.load_from_code()`로 모델을 fresh
  weights로 인스턴스화한 뒤 `load_state_dict()`로 채운다 — **그대로 재사용 가능**.
- 단, `model_source == "loaded"`(모델 탭에서 사용자가 직접 붙여넣은 커스텀 아키텍처)인
  경우 `load_model_from_ckpt()`는 `None`을 반환한다. 이유: 체크포인트에는 소스 코드가
  저장되지 않고 태그 문자열만 있음(2026-08-20 기획 로그에서 이미 확인된 사실). 기존
  `inference_tab.py`는 이 경우 `win._model_tab.loaded_model`(같은 세션의 모델 탭 인메모리
  상태)로 폴백하는데, **이는 정확히 이번 도구가 배제해야 할 탭 간 교차 의존**이다.
- **대응**: 체크포인트 선택 시 `load_checkpoint_meta()`로 `model_source`를 먼저 읽는다.
  - `preset:*` → 자동 인스턴스화(추가 UI 없음).
  - 그 외("loaded" 또는 구형 체크포인트로 정보 없음) → 탭 안에 모델 코드 입력 박스를
    노출하고, 모델 탭과 동일한 두 단계(Validate → Load)로 `app/core/model_validator.py`의
    `validate(code)` + `app/core/model_loader.py`의 `load_from_code(code)`를 **그대로**
    호출한다. 둘 다 Qt/프로젝트 의존성 없는 순수 함수라 이식에 문제없음. 단
    `model_loader.save_user_code()`는 프로젝트의 `user_models_dir()`에 파일을 쓰므로
    **호출하지 않는다**(붙여넣은 코드는 세션 동안만 메모리에 유지, 디스크에 저장하지
    않음 — 독립성 유지).

## 판단 4 — 타겟(녹) 클래스 정의: 프로젝트 `classes.json` 미사용

`inference_engine.run()`은 내부에서 무조건 `annotation_store.load_classes()`를 호출하는데,
이는 `_project.classes_file()`(현재 열려 있는 프로젝트의 `classes.json`)을 읽는다. 이 신규
탭이 살아있는 동안 `MainWindow`에는 항상 어떤 프로젝트든 열려 있으므로(`main.py`가
프로젝트 선택 후에만 `MainWindow`를 생성) `_project.current()`가 `None`이 되는 경우는
실제로는 없지만, **그 프로젝트의 클래스 정의가 지금 로드한(어디서 왔는지 모르는) 체크포인트와
아무 관계가 없을 수 있다** — 이름/색상이 틀리게 표시될 실질적 정확성 위험이 있음(단순한
"독립성 원칙 위반" 수준이 아니라 실사용 버그).

**대응(최소 침습)**: `inference_engine.run()` / `run_sliding_window()` / `refilter()`에
`classes: list[ClassDef] | None = None` 선택 인자를 추가한다(3곳 각 1~2줄). `None`이면
기존과 동일하게 `load_classes()` 폴백 — **기존 4탭 호출부는 인자를 안 넘기므로 동작
변화 없음(회귀 위험 없음)**. 신규 탭은 항상 이 인자를 명시적으로 채워서 넘긴다.

이 탭에서 `classes` 리스트를 만드는 방법은 프로젝트 파일을 읽지 않고, **추론 1회 실행 후
반환된 `raw_class_map`의 고유값(배경 0 제외)으로부터 즉석 구성**한다 — 클래스 이름/색상을
사용자가 미리 입력할 필요가 없다:
- `raw_class_map`에 등장하는 배경 아님 클래스 id가 1개뿐이면 자동으로 그 id를 "타겟(녹)"으로
  선택하고 기본 이름 "class_1"(수정 가능한 텍스트 필드 제공, 자유 표기 "녹" 등)을 부여.
- 2개 이상이면 드롭다운으로 사용자가 타겟 id를 고른다(v1 범위는 아래 "결정 필요" 참고).
- 색상은 기존 `annotation_store.DEFAULT_PALETTE`(프로젝트 의존 없는 모듈 레벨 상수)를
  그대로 재사용해 `class_id`로 인덱싱 — 새 팔레트 발명 없음.

체크포인트에 클래스 메타데이터 자체를 저장하는 근본 해결(=`app/core/trainer.py`가
`config["classes"]`도 함께 저장)은 `trainer.py`(공유 파일, 기존 4탭 학습 플로우에 영향)를
건드려야 하는 별개 스코프라 **이번 기능 범위 밖으로 명시적으로 제외**한다. 향후 후보로만
기록(아래 "향후 확장 후보").

## 데이터 흐름

```
1. 이미지 로드(QFileDialog, 프로젝트 밖 임의 경로)
2. 체크포인트 로드(QFileDialog, *.pt)
   → load_checkpoint_meta()로 model_source 확인
   → preset: 자동 인스턴스화 / 그 외: 모델 코드 붙여넣기(Validate→Load)
3. 추론 실행 (engine.run 재사용, classes=None으로 1차 실행해 raw_class_map 확보
   → 고유 클래스 id로 즉석 ClassDef 구성 → 필요시 engine.refilter로 classes 반영해 재컬러화)
4. 동심원 정의
   4a. 자동 검출(Canny+findContours+원형도/면적 필터+강건한 원피팅, 판단 2 최종본) —
       원본을 다운스케일(기존 _MAX_OVERLAY_DIM=2048 관례 재사용)해 검출 후 중심/반지름을
       원본 스케일로 역산
   4b. 수동 편집 — 드래그로 추가/이동/반지름 조절/삭제
5. 존별 마스크 계산 (zone_metrics.zones_from_circles)
6. 존 선택 → 해당 존 마스크 AND 타겟 클래스 마스크 → 퍼센티지 표시
7. (선택) 블랍 클릭 삭제 → 타겟 마스크에서 해당 connected component 제거 → 6 재계산
```

3~7단계는 전부 numpy/cv2 배열 연산이라 재계산 비용이 낮음(5472×3648 기준, 다운스케일
없이도 500ms 미만대 예상 — 실측은 구현/검증 단계에서 확인).

## UX 흐름 상세

### 원 검출/편집

- "자동 검출" 버튼 + 민감도 슬라이더 1개(내부적으로 Canny 임계값+원형도 필터 매핑,
  판단 2 최종본의 Canny+findContours+원피팅 파이프라인) — v1은 파라미터 노출을 최소화
  (라더: 필요해지면 그때 추가). 정확한 매핑값은 아래 "라운드 분할" 라운드 2의 스크립트
  프로토타입 결과로 확정.
- 검출 결과는 캔버스 위에 반투명 원 핸들(드래그 가능한 테두리 + 중심점)로 표시.
- 수동: 캔버스 빈 곳 드래그로 새 원 생성(중심 클릭 후 반지름까지 드래그), 기존 원
  테두리/중심 드래그로 이동·반지름 조절, 원 선택 후 Delete 키 또는 우클릭 메뉴로 삭제.
  (**2026-08-25 2차 수정**: 1차 수정에서 검토했던 폴리곤 정점 드래그/삽입/삭제는 데이터
  모델이 다시 원으로 확정되며 불필요해짐 — 원 편집은 중심점 이동 + 반지름 핸들 조절
  2가지 조작만 있으면 되므로 구현 난이도가 크게 낮아짐.)
- 원 목록은 반지름 오름차순으로 자동 정렬해 사이드 패널에 표시(중심부→바깥쪽 순).

### 존 선택 및 네이밍

- 존 개수 = 원 개수 + 1 (중심부 1 + 원 사이 고리 (N-1) + 바깥쪽 1, 원이 1개뿐이면 중심부/
  바깥쪽 2개).
- 네이밍 제안: `중심부`(최소 원 내부), `링 1`, `링 2`, …, `링 N-1`(인접 원 사이),
  `바깥쪽`(최대 원 밖, 이미지 경계까지).
- 캔버스에서 존 클릭 또는 사이드 리스트에서 존 클릭 → 해당 존 하이라이트 + 퍼센티지 표시.
  리스트는 항상 전체 존의 퍼센티지를 한번에 보여주고(요구사항이 "클릭 등으로 선택"이라
  구체 인터랙션을 정했으므로), 클릭은 캔버스 하이라이트 포커스 이동 용도로 둔다.

### 존 계산 로직 — 원판(disk) 마스크 집합 연산 (2026-08-25 2차 수정: fillPoly→원 마스크로 복귀)

두 인접 원 각각을 이진 마스크로 채운 뒤 차집합을 구한다:

1. `mask_i = np.zeros(img_shape, uint8)`; `cv2.circle(mask_i, (int(cx_i), int(cy_i)),
   int(r_i), 1, thickness=-1)` (또는 벡터화 거리식 `(xx-cx)**2+(yy-cy)**2 <= r**2` —
   둘 다 `cv2`/`numpy` 표준 기능이라 신규 의존성 없음, 원 데이터가 이미 있으므로 폴리곤
   `fillPoly`보다 이쪽이 더 단순).
2. 원을 반지름 오름차순 `[C_0(최소), C_1, …, C_{N-1}(최대)]`로 정렬했을 때:
   - `Zone_center = mask(C_0)` (최소 원 내부 자체가 하나의 존).
   - `Zone_i = mask(C_{i+1}) AND NOT mask(C_i)` for `i = 0 .. N-2` (바깥쪽 원 마스크에서
     안쪽 원 마스크를 뺀 고리형 존).
   - `Zone_outside = 전체 이미지 마스크 AND NOT mask(C_{N-1})` (최대 원 밖, 이미지 경계까지
     — 기존과 동일하게 기본 포함).
3. 각 `Zone_k` 마스크와 타겟 클래스 이진 마스크를 AND한 뒤 픽셀 카운트 비율로 퍼센티지 산출
   (기존 판단 4의 즉석 클래스 구성과 동일 소스).
4. **"원 안에 원이 있으면 하위 원의 영역은 포함되지 않는다" 명시적 재확인**(사용자 2차
   정정 원문) — 위 `Zone_i = mask(바깥) AND NOT mask(안쪽)` 정의가 인접한 두 원 쌍뿐
   아니라 반지름 오름차순 정렬 후 항상 적용되므로, **임의의 원 내부에 더 작은 원(들)이
   있으면 그 내부 영역은 항상 자동으로 제외**되는 것이 일반적으로 성립한다(정렬 후
   인접 쌍 차집합 방식이 이를 자동으로 만족 — 별도 특수 로직 불필요).
5. **전제 조건 명시**: 이 연산은 원들이 대략 nested(바깥 원이 안쪽 원을 완전히 포함)라는
   것을 전제로 한다 — 배터리 캡의 실제 물리 구조상 항상 성립. 만약 사용자가 수동 편집으로
   원을 서로 교차하게 만들면(비정상 입력) `Zone_i`가 예상과 다른 모양이 될 수 있으나 이는
   입력 데이터 오류이지 연산 자체의 결함이 아님 — v1에서는 별도 경고/방지 로직을 추가하지
   않는다(발생 가능성 낮고, 방지하려면 복잡한 기하 검증이 필요해 YAGNI).

### 블랍 삭제

- 타겟 클래스 이진 마스크에 `cv2.connectedComponentsWithStats(mask, connectivity=8)`로
  라벨맵 생성(기존 `inference_engine._compute_blobs_and_filter()`와 동일 API, 다만 이
  탭은 단일 이진 마스크 + 클릭 삭제 전용이라 별도의 작은 헬퍼로 둠 — confidence/size
  threshold 필터링 로직까지 그대로 가져오면 이 도구엔 불필요한 결합이 생김).
- 캔버스 클릭 → 화면 좌표를 이미지 좌표로 역변환(줌/팬 반영, `overlay_viewer.py`의
  `mc`→`mi` 변환 공식 재사용) → 라벨맵에서 해당 좌표 라벨 조회 → 배경(0)이 아니면 삭제
  대상 집합에 id 추가 → 표시 마스크에서 `np.isin(labels, removed_ids)` 위치를 배경 처리
  → 존 퍼센티지 재계산 트리거.
- 삭제 취소(Undo) 1단계는 있으면 좋지만 v1 필수 아님(라벨링 탭처럼 무한 undo 스택까지는
  과함 — 필요성이 확인되면 후속 라운드에서 검토).

     로컬 스크립트로 반복 실행해 결과를 이미지로 저장·육안 확인. **특히 녹(불량)이 있는
     영역에서도 피팅된 원이 실제 원형에서 벗어나지 않는지**(이번 2차 수정의 핵심 요구사항)
     를 확인하는 것이 목적 — 실사용 가능한 기본 파라미터 세트 확보. 스파이크(기술 선택지
     비교)는 아님, 이미 파이프라인 구조는 확정됐고 파라미터만 정하는 구현 준비 단계라
     별도 스파이크 에이전트 불필요. 이 스텝에서 "이 이미지셋으로는 실용적 파라미터를
     못 찾는다"는 결론이 나오면 그때 리더에게 보고(스파이크 필요 여부 재검토).
   - **2b. 위젯 구현** — 2a에서 확정한 파라미터를 `circle_detector.py` 기본값으로 반영해
     `ZoneCanvas`에 자동검출 버튼 + 수동 원 편집(추가·이동·반지름 조절·삭제) 연결.
   검증: 실제 예시 이미지(특히 녹 있는 영역 포함)로 자동검출 결과 육안 확인 + 수동 편집
   (드래그 이동/반지름 조절/추가/삭제) 왕복.
3. **라운드 3** — `zone_metrics.py` 신설(Circle/Zone 데이터클래스, 원 마스크 기반 집합
   차집합) + 존 리스트 패널 + 퍼센티지 계산·표시(원 변경 시 실시간 재계산). 검증: 소규모
   합성 마스크로 픽셀 카운트 수작업 검산 일치 확인.
4. **라운드 4** — 블랍 클릭 삭제 + 재계산. 검증: 합성 이미지(여러 블랍)로 특정 블랍만
   삭제되고 나머지 유지·퍼센티지 정확히 갱신되는지 확인.

각 라운드는 기존 관례(R1~R6, UI/UX 재편 등)와 동일하게 구현 → 실제 `python main.py`
구동 검증 → 다음 라운드 순으로 진행.

## 리스크 / 주의사항

- 5472×3648(20MP) BMP 이미지 — 기존 관례(`_MAX_OVERLAY_DIM=2048`)를 그대로 따라 화면
  표시/검출용 다운스케일과 저장/계산용 원본 해상도를 분리 유지해야 함(기존
  `inference_engine.py`/`annotation_canvas.py`가 이미 이 패턴을 쓰고 있어 신규 코드도
  동일 관례 적용).
- Canny+findContours+원피팅은 Hough 단독 대비 파라미터(임계값·원형도·면적 필터·이상치
  제거 반복횟수)에 더 민감할 수 있음 — 라운드 2a 스크립트 프로토타입에서 실제 예시
  이미지(특히 녹이 있는 영역)로 먼저 검증(위 라운드 분할 참고). 특히 강건한 원피팅이
  이상치(불량 튀어나온 에지)를 실제로 걸러내는지가 이번 2차 수정의 핵심 확인 포인트.
- 존 계산(원 마스크 차집합)은 원들이 대략 nested라는 전제 — 배터리 캡 실제 구조상 항상
  성립하지만, 수동 편집으로 비정상 교차 입력을 만들면 결과가 왜곡될 수 있음(v1은 방지
  로직 없음, "존 계산 로직" 절 참고).
- `inference_engine.py`는 기존 4탭이 공유하는 파일 — `classes` 옵션 인자 추가가 기존
  호출부(`inference_tab.py`)에 회귀를 일으키지 않는지 검증 단계에서 반드시 확인.
- 커스텀 모델 코드 입력 경로는 `model_validator.py`/`model_loader.py`의 기존 샌드박스
  정책(`docs/SECURITY.md`)을 그대로 따름 — 신규 우회 경로를 만들지 않음.
