## 요청 1 — "프로젝트를 클릭하면 자동으로 열리게 해달라" (2026-08-20 사용자 재확인으로 정정)

**최초 판단은 틀렸음.** 앱 내부 "최근 프로젝트 목록"의 클릭 방식(싱글/더블) 문제가 아니었다.
사용자 재확인 원문: "외부에서 따로 확장자를 만들어주고 해당 프로젝트 확장자를 더블클릭시 바로
열리게 해달라는 의미였어" — 즉:

1. 프로젝트를 나타내는 **전용 파일 확장자**(예: `.segproj`)를 만든다.
2. Windows 파일 탐색기에서 그 파일을 **더블클릭하면 OS가 이 앱을 실행하면서 해당 프로젝트를
   바로 연다** — 워드 파일 더블클릭하면 Word가 그 문서를 열고 실행되는 것과 같은 방식.

### 이게 왜 별도 라운드가 아니라 exe 패키징에 종속되는가

Windows에서 "확장자 더블클릭 → 특정 프로그램 실행"은 **파일 연결(file association)**을
레지스트리에 등록해야 동작한다(`HKEY_CLASSES_ROOT`에 확장자→ProgID→실행 커맨드 매핑). 이건
보통 **설치 프로그램(installer)이 설치 시점에 등록**하는 절차다 — `python main.py` 개발 실행
방식에서는 실질적으로 아주 어색하다(파일 연결 커맨드를 `pythonw.exe main.py %1` 식으로 걸어야
하고, 사용자 환경마다 파이썬 경로·가상환경이 달라 깨지기 쉬움). 반면 exe 패키징(PyInstaller
등)이 되어 있으면 설치 프로그램이 "이 확장자는 SegmentationTool.exe로 연다"를 표준적으로
등록해줄 수 있다.

**결론**: 이 요청은 [docs/roadmap.md](../roadmap.md)의 "exe 패키징 + Setup Guide" 항목(2026-08-20
접수, "추후" 착수로 사용자가 이미 확정)에 **하위 요구사항으로 편입**한다 — 별도로 지금 스코프를
잡지 않는다. exe 패키징 착수 시 함께 설계할 것:
- 프로젝트 폴더를 가리키는 마커 파일(예: `project.json`을 열 게 아니라, 프로젝트 폴더 자체를
  가리키는 `{project_name}.segproj` 같은 얇은 포인터 파일 — 프로젝트 자체는 계속 폴더 구조로
  유지하고, 이 파일은 "이 경로를 열어라"는 참조만 담는 안이 유력. 프로젝트 전체를 하나의
  파일로 바꾸는 건 아님 — 그건 위 "요청 2"의 export/import 기능과는 다른 목적).
- `main.py`가 커맨드라인 인자(`sys.argv[1]`, OS가 더블클릭 시 파일 경로를 인자로 넘겨줌)를
  받아 `project_start_dialog.py`를 건너뛰고 바로 해당 프로젝트로 `MainWindow`를 여는 경로 추가.
- 파일 연결 레지스트리 등록은 exe 설치 프로그램(Inno Setup 등) 스크립트에서 처리.

`docs/decisions-needed.md`의 관련 항목은 삭제(더 이상 "싱글/더블클릭" 판단 문제가 아니므로) —
근거는 이 절에 보존.

## 요청 2 — "프로젝트 전체를 내보내거나 하나의 파일로 통합해달라"

### 코드 현황

- `app/core/project.py`의 `Project` 데이터클래스: `images_dir`, `thumbs_dir`(`.thumbs` 캐시),
  `annotations_dir`, `checkpoints_dir`, `user_models_dir`, `classes_file`, `meta_file`
  (`project.json`) 프로퍼티로 프로젝트 폴더 구조를 정의. `ensure_dirs()`가 표준 5개 하위
  디렉토리를 보장.
- `app/widgets/export_dialog.py`(기존 "내보내기" 기능)는 **라벨 데이터만** 대상으로 한다 —
  이미지+어노테이션을 JSON/YOLO-seg/COCO 포맷으로 변환해 지정 폴더에 풀어놓는 것이지, 프로젝트
  폴더 자체를 압축하거나 체크포인트·모델 코드를 포함하지 않는다. `classes.json`은 JSON 포맷
  내보내기에만 포함, YOLO는 `classes.txt`로 별도 생성.
- 체크포인트 재현성: `trainer.py`가 `.pt`에 저장하는 `config.model_source`는 실제 소스 코드가
  아니라 태그 문자열(`"loaded"` 또는 `"preset:<key>"`)이다. `inference_engine.load_model_from_ckpt()`는
  `preset:*` 태그만 자동 인스턴스화 가능하고, `"loaded"`(사용자가 모델 탭에 직접 붙여넣은 커스텀
  코드)는 **자동 복원이 안 되며 사용자가 모델 탭에서 코드를 다시 로드해야 함**. 즉
  `user_models_dir`에 저장된 `.py` 파일이 체크포인트와 자동 연결되어 재로딩되는 구조가 아니다
  (이는 기존부터 있던 별개의 갭이며 이번 스코프에서 고치라는 요청은 없었음 — 참고용으로만 기록).
  → 이 사실은 "체크포인트 포함 여부"와 별개로 "user_models 포함 여부" 판단에 영향: 커스텀 모델
  코드 자체(텍스트, 수 KB)는 백업·이전 목적에 필수적이지만, 포함한다고 해도 checkpoint와 자동
  연결되어 즉시 추론 가능해지는 것은 아니라는 한계를 사용자에게 안내할 필요가 있다.
- `.gitignore`(20, 28~29행)가 `projects/*/checkpoints/`, `*.pt`, `*.pth`를 이미 추적 대상에서
  제외하고 있음 — 프로젝트 관례상 체크포인트는 "무겁고 재생성 가능한 산출물"로 취급되고 있다는
  근거로 기본값 판단에 참고.
- QThread 진행률 워커 기존 패턴 확인: `app/widgets/image_browser.py`의 `_FolderImportWorker(QThread)`
  — 폴더 스캔/복사를 백그라운드로 돌리고 진행률 시그널을 방출하는 기존 관례. zip 압축 워커도
  이 패턴을 그대로 따를 수 있음.

### 제안 스코프

**export + import 둘 다 필요.** export 단독으로는 "통합 파일로 만들어달라"는 요청의 실질 목적
(백업/다른 PC로 이전/공유)을 절반만 충족한다 — 만든 zip을 다시 프로젝트로 되돌릴 방법이 없으면
사실상 "보기용 아카이브"에 그친다. 다만 리스크가 export보다 크므로(경로 충돌, 잘못된 zip 구조,
기존 프로젝트 덮어쓰기 등) **아래처럼 라운드를 분리**한다.

#### 라운드 A — 프로젝트 전체 내보내기 (export, 저~중리스크)

- **신규 다이얼로그** `app/widgets/project_export_dialog.py` 신설(기존 `export_dialog.py` 확장이
  아니라 분리 — 대상 개념이 다름: 기존은 "라벨 포맷 변환 내보내기", 신규는 "프로젝트 원본 그대로
  패키징". 같은 클래스에 넣으면 체크박스 의미가 헷갈리고 두 기능의 진행률/에러 처리 로직도
  성격이 다름).
- 진입점: `project_start_dialog.py`에 최근 프로젝트 항목 대상 "내보내기" 버튼(또는 우클릭
  컨텍스트 메뉴) 추가 — 프로젝트를 열지 않고도 내보낼 수 있어야 백업 목적에 맞음. 추가로
  현재 열려있는 프로젝트를 대상으로 하는 진입점을 메인 윈도우(예: 파일 메뉴 또는 설정 다이얼로그
  근처)에도 둘지는 디자인 단계에서 배치 확인.
- 압축 대상: `images/`(단, `.thumbs/` 캐시는 재생성 가능하므로 **제외**), `annotations/`,
  `classes.json`, `project.json` — 이 4가지는 **항상 포함**(기본이자 필수, 체크박스 없음).
  `checkpoints/`, `user_models/`는 **체크박스로 선택**, 기본값:
  - `checkpoints/` — **기본 미체크**(대용량 `.pt`, `.gitignore` 관례와 일치, 원하면 켜서 포함).
  - `user_models/` — **기본 체크**(텍스트 파일이라 용량 부담 적고, 커스텀 모델 코드 자체는
    백업 목적상 핵심 자산에 가까움 — 단, 위에서 확인한 대로 체크포인트 자동 연결은 안 되므로
    다이얼로그에 "커스텀 모델은 가져오기 후 모델 탭에서 다시 로드해야 합니다" 안내 문구 필요).
  - 두 기본값 모두 사용자 확인 필요 → `decisions-needed.md` 등록.
- 포맷: zip(표준 라이브러리 `zipfile`, 외부 의존성 추가 없음. `requirements.txt`에 없는
  `py7zr` 등은 배제).
- 대용량 대응: 실측 없이 "오래 걸릴 수 있다"고만 가정하지 않고, `_FolderImportWorker` 패턴을
  따르는 `_ProjectExportWorker(QThread)`로 백그라운드 압축 + 진행률 시그널(파일 수 기준)
  필수 적용 — 프로젝트 특성상 이미지 수백~수천 장(대규모 합성 프로젝트 사례가 R6 로그에도
  언급됨) + 개별 파일 50MB급 가능성을 이미 알고 있으므로, 스파이크 없이 바로 워커 패턴 채택
  (신규 라이브러리 선택이 아니라 기존 관례 재사용이라 스파이크 불필요).
- zip 파일명 제안: `{project_name}_{yyyymmdd}.zip`, 저장 위치는 `QFileDialog.getSaveFileName`.

#### 라운드 B — 프로젝트 가져오기 (import, 중~고리스크) — **2026-08-20 사용자 결정: A와 함께 이번에 진행**

- zip을 선택하면 압축 해제 후 `Project` 구조 검증(`images/`, `annotations/`, `classes.json`
  존재 확인) → 대상 위치(기본 `get_projects_root()` 하위에 원래 이름, 이름 충돌 시 처리 필요)에
  풀고 `proj.open_existing()`으로 등록.
- 리스크가 export보다 큰 이유:
  - **경로 충돌 — 결정됨(리더 기본값 채택, 안전 우선)**: 같은 이름의 프로젝트가 이미 존재하면
    **절대 덮어쓰지 않고 자동으로 이름을 바꾼다**(`{name}_imported`, 이미 그것도 있으면
    `{name}_imported_2`... 식으로 충돌 없을 때까지 증가). 사용자에게 매번 물어보는 방식은
    가져오기 다이얼로그 흐름을 복잡하게 만들고, 자동 이름 변경은 기존 프로젝트를 파괴할 위험이
    없는 가장 안전한 기본값이라 별도 확인 없이 이 방식으로 확정. 가져오기 완료 후 결과 다이얼로그에
    "OO_imported 이름으로 저장됨" 안내만 명확히 표시.
  - **zip 내용 검증**: 임의의 zip(다른 도구로 만든 손상 파일, 필수 폴더 누락, 경로 탈출
    `../../` 포함 zip 등)을 방어적으로 처리해야 함 — `zipfile` 압축 해제 시 경로 정규화 검증
    필수(zip slip 취약점 우회 목적이 아니라도 방어적으로 필요).
  - **버전 호환성**: 내보낸 프로젝트가 다른(더 오래된/새로운) 앱 버전에서 만들어졌을 가능성 —
    당장은 스키마 버저닝이 없으므로 최소한 "가져온 프로젝트에 손상 파일이 있을 수 있다" 경고
    수준으로 시작하고, 정식 버전 체크는 이번 스코프 밖으로 명시.
  - **zip 내용 검증**: 임의의 zip(다른 도구로 만든 손상 파일, 필수 폴더 누락, 경로 탈출
    `../../` 포함 zip 등)을 방어적으로 처리해야 함 — `zipfile` 압축 해제 시 경로 정규화 검증
    필수(zip slip 방지).
  - **버전 호환성**: 당장은 스키마 버저닝이 없으므로 "가져온 프로젝트에 손상 파일이 있을 수
    있다" 경고 수준으로 시작, 정식 버전 체크는 이번 스코프 밖.
  - 진입점: 라운드 A와 동일하게 `project_start_dialog.py`에 "가져오기" 버튼 추가(새 프로젝트/
    프로젝트 열기 옆, 또는 별도 줄).
- **구현 순서**: 사용자가 A·B를 함께 진행하기로 했지만, **코드 의존관계상 A(export 포맷 확정)가
  먼저 구현·검증되어야 B(import)가 그 zip 구조를 전제로 만들어질 수 있다** — 같은
  요청 안에서 순차 진행(A 구현→검증 통과 확인 후 곧바로 B 구현→검증, 사용자에게 별도 재확인 없이
  이어서 진행).

### 실행 순서 제안

1. **요청 1은 이 스펙 범위에서 제외** — exe 패키징(`docs/roadmap.md`, "추후" 착수)에 하위
   요구사항으로 편입, 위 "요청 1" 절 참고.
2. 요청 2 라운드 A(export): 구현(`project_export_dialog.py` + `_ProjectExportWorker`) →
   검증(대용량 합성 프로젝트로 진행률/취소/에러 케이스 실행 확인, "주요 기능 추가"이므로
   골든패스 수준 검증 요청). 새 다이얼로그가 기존 `export_dialog.py`/`_FolderImportWorker`
   패턴을 그대로 따르는 정형화된 구조라 별도 디자인 목업 없이 바로 구현.
3. 요청 2 라운드 B(import): 라운드 A 검증 통과 직후 이어서 구현 → 검증. 이름 충돌은 자동
   리네임으로 확정(위 참고).
