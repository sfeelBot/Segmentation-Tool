## Issue #9 — 라벨링 화면 줌인/줌아웃 시 초점이 맞지 않는 버그

GitHub 원문: "마우스 왼쪽 클릭(드래그) 형태에서 줌인/줌아웃할 때 초점이 맞춰지지 않는 현상 발생"

### 문제 정의

`app/widgets/annotation_canvas.py`의 줌 로직(`wheelEvent()`)이 좌클릭 드래그로 패닝하는
도중에 사용되면 커서 위치에 줌 초점이 고정되지 않고 화면이 튀는 현상.

### 코드 조사 결과 (확정)

- 앱 전체에서 줌을 트리거하는 경로는 **`AnnotationCanvas.wheelEvent()`(마우스 휠 스크롤)
  단 하나뿐**. 버튼/단축키/드래그 줌 등 다른 진입점 없음 — `labeling_tab.py`에 `zoom`
  키워드 매치 0건으로 확인.
- `wheelEvent()` 자체의 커서 앵커링 공식은 수학적으로 정확함:
  ```python
  mouse_canvas = QPointF(event.position())
  mouse_img = self._c2i(mouse_canvas)          # 줌 전 커서의 이미지 좌표
  self._zoom = clamp(self._zoom * factor)
  self._pan = mouse_canvas - QPointF(mouse_img.x() * self._zoom, mouse_img.y() * self._zoom)
  ```
  검산: 새 `_pan`/`_zoom`으로 `_c2i(mouse_canvas)`를 다시 계산하면 정확히 `mouse_img`로
  돌아옴 — 단독 실행 시 커서가 항상 같은 이미지 지점에 고정됨. **정지 상태에서의 휠 줌은
  정상.**
- **원인 후보 (코드로 확정, 최우선)**: 좌클릭 드래그로 패닝 중(Pan 도구 활성 + 좌클릭
  드래그, 또는 Space+좌클릭 드래그 — 우클릭 드래그도 동일 코드경로라 동일 결함이지만 이슈
  원문은 좌클릭만 언급) 상태에서 휠로 줌을 하면 초점이 어긋난다.
  - `mousePressEvent()`가 패닝 시작 시 `_pan_start_mouse`/`_pan_start_offset`을 **1회만**
    캡처(581~624행 부근).
  - 드래그 중 `mouseMoveEvent()`의 패닝 분기(724~728행)는 매번
    `self._pan = self._pan_start_offset + (pos - self._pan_start_mouse)`로 **절대
    재계산**한다.
  - `wheelEvent()`가 드래그 도중 `self._zoom`/`self._pan`을 갱신해도 `_pan_start_offset`/
    `_pan_start_mouse`는 그대로 남는다 — 휠 직후 마우스가 조금이라도 움직이면 다음
    `mouseMoveEvent()`가 방금 휠이 계산해둔 커서-고정 `_pan` 값을 **옛 시작값 기준으로
    덮어써버린다**. 이것이 "왼쪽 클릭(드래그) 형태에서 줌인/줌아웃할 때 초점이 맞춰지지
    않는" 원문 증상과 정확히 일치.
  - Select 도구의 사각선택/이동 드래그, 브러시 스트로크 드래그는 좌표를 이미지 좌표
    (`_c2i()`로 매 이벤트 재계산)로 다루므로 이 결함의 영향을 받지 않음 — **패닝 드래그
    (`_pan_active`)만 해당하는 결함으로 범위가 좁혀짐**.

### 제안 수정 방향 (참고용 — 최종 설계는 구현 에이전트)

`wheelEvent()`에서 패닝 드래그가 진행 중(`self._pan_active`)이면, 줌 적용 직후
`_pan_start_offset`/`_pan_start_mouse`도 함께 갱신해 드래그의 기준점을 새 pan/zoom에
맞게 재설정한다:
```python
if self._pan_active:
    self._pan_start_offset = QPointF(self._pan)
    self._pan_start_mouse = mouse_canvas
```
다른 파일 영향 없음(줌 진입점이 `annotation_canvas.py` 하나뿐).

### 재현조건 특정 관련 — 리더가 필요 시 사용자에게 확인할 질문 목록

다음 질문을 남겨둔다(이번 라운드에서 직접 사용자에게 묻지 않음):

1. 줌은 마우스 휠 스크롤로 하신 것이 맞나요? (앱에 휠 스크롤 외 다른 줌 수단이 없음을
   코드로 확인했습니다.)
2. "왼쪽 클릭(드래그) 형태"란 이미지를 드래그해서 이동(패닝)하던 도중이라는 뜻인가요?
   그렇다면 그 방법은: (a) 상단 도구모음에서 Pan(이동) 도구를 선택한 상태, (b) Space
   키를 누른 채 좌클릭 드래그, (c) 다른 도구(브러시/폴리곤/선택) 활성 상태에서 좌클릭
   드래그 중이었나요?
3. 패닝 드래그 도중(마우스 버튼을 누른 채로) 휠을 스크롤해 줌을 하셨나요, 아니면 드래그를
   끝낸 직후에 줌을 하셨나요?

### 구현이 건드릴 파일

- `app/widgets/annotation_canvas.py` — `wheelEvent()`(+ 필요 시 `mouseMoveEvent()`의
  패닝 분기) 최소 수정. 다른 파일 영향 없음.

### 검증 골든 패스

1. Pan 도구(또는 Space+좌클릭) 드래그로 이미지를 이동시키는 도중 마우스 휠로 줌인/줌아웃
   → 커서가 가리키는 이미지 지점이 줌 전후 동일한 화면 위치에 유지되는지 확인.
2. 드래그 없이 정지 상태에서의 휠 줌(기존 정상 동작) 회귀 없는지 확인.
3. 우클릭 드래그(패닝) 도중 휠 줌도 동일 결함이 있었으므로 회귀 없는지 함께 확인 권장
   (원 이슈엔 명시 안 됐지만 같은 코드 경로 공유).
4. Select 도구 이동/사각선택 드래그, 브러시 스트로크 도중 휠 줌 시 문제없음(원래도
   정상이었음 — 회귀 없음) 확인.

## Issue #8 — 이미지탭 다중선택 + 삭제 기능

GitHub 원문: "이미지탭 쪽에서 다중선택 기능 추가 및 다중선택 후 삭제 할 수 있는 기능.
이미지탭에서 삭제할 수 있는 기능."

### 중요 발견 — 코드상 이미 구현되어 있음

`app/widgets/image_browser.py`(라벨링 탭의 이미지 브라우저, "이미지탭"으로 지칭된 것으로
판단)를 전수 조사한 결과, 요청 3가지가 전부 이미 존재함:

1. **다중선택**: `_tree`(`QTreeWidget`)가 이미
   `setSelectionMode(QTreeWidget.SelectionMode.ExtendedSelection)`로 설정돼 있어
   Ctrl/Shift 클릭 기반 표준 파일탐색기식 다중선택이 이미 가능(`_build_ui()`).
2. **다중선택 후 삭제**: `_on_delete()`가 `self._tree.selectedItems()`로 선택된 항목
   전체를 순회하며 처리.
3. **삭제 기능 자체**: 상단 `Delete` 버튼(`_btn_del`) → `_on_delete()`가 이미:
   - 이미지 파일 삭제
   - 대응하는 `annotations_dir()/{stem}.json` 어노테이션도 함께 삭제
   - 삭제 전 `QMessageBox.question()` 확인 다이얼로그 필수 경유(1개 선택 시 파일명 명시,
     2개 이상은 최대 3개 미리보기 + "외 N개" 요약 문구)
   - "아니오" 선택 시 아무 것도 지우지 않고 종료
   - 삭제 후 `reload()`로 목록 즉시 갱신

### 과거 관련 버그(`unhashable QTreeWidgetItem`) 확인 — 이미 해소됨

- `data/logs/errors.log`에 **2026-05-27**자 크래시 로그 3건 존재:
  `self._item_to_path[item] = p` — `QTreeWidgetItem`을 **dict 키로 사용**해
  `TypeError: unhashable type: 'QTreeWidgetItem'`.
- 현재 코드에는 이 패턴(`_item_to_path[item] = ...`)이 완전히 사라짐 — Path를 키로 쓰는
  `_path_to_item: dict[Path, QTreeWidgetItem]`(역방향) + 아이템→Path 역조회는
  `item.data(0, _PATH_ROLE)`(UserRole)로 대체돼 있음(60~61행, 396~406행). 즉 옛 설계
  자체가 지금은 존재하지 않아 이 형태의 크래시는 현재 코드에서 재현 불가능한 구조.
- `docs/agents/verification-log.md` 2026-08-20 항목도 이 로그를 "오래된 로그, 이번
  라운드와 무관"으로 이미 확인했었음. 다만 그 항목은 "QA.md에서 별도 추적 중"이라고
  서술했는데, 실제 `QA.md` Open/Closed 어디에도 이 버그가 정식 등록돼 있지 않음(문서
  정합성 갭 — 실제 코드 결함 자체는 해소된 것으로 보임, QA.md 미등록은 별개 사소한 이슈라
  이번 라운드에서 손대지 않음).

### 스코프 판단

- **신규 구현이 불필요할 가능성이 높음.** 코드가 이미 존재하는데 다시 만들지 않는다
  (같은 기능 중복 구현 방지).
- 이번 라운드는 **검증 우선**: 실제 GUI에서 Ctrl/Shift 다중선택 + Delete 버튼 클릭이
  의도대로 동작하는지, 어노테이션 JSON도 함께 삭제되는지, 크래시 없는지(과거
  `unhashable` 류 재현 여부 포함) 확인. 문제가 실제로 발견되면 그때 최소 침습 수정으로
  넘어간다.
- **선택적 저비용 갭 1건**: 키보드 `Delete` 키로 바로 삭제하는 단축키가 없음(버튼 클릭만
  가능, `_tree`에 `keyPressEvent` 오버라이드 없음 확인). GitHub 원문이 명시적으로
  요구하진 않았으나 "표준 파일탐색기식 다중선택"이라는 기대에는 `Delete` 키 지원이
  포함될 수 있음. 우선순위 낮음 — 필요 시 구현 에이전트가 `_tree`에 `Delete` 키 핸들러를
  추가해 `_on_delete()`를 호출하는 수 줄 수정으로 해결 가능.

### 구현이 건드릴 파일 (예상, 검증 결과에 따라 변동)

- 검증만으로 끝날 경우: 없음.
- `Delete` 키 단축키만 추가할 경우: `app/widgets/image_browser.py`(수 줄).
- 검증 중 실제 결함이 발견될 경우: 같은 파일 내 최소 수정.

### 검증 골든 패스

1. 이미지 여러 장이 있는 프로젝트에서 Ctrl+클릭으로 비연속 다중 선택 → Delete 버튼 클릭
   → 확인 다이얼로그에 선택 개수·미리보기가 정확히 표시되는지.
2. "예" 클릭 후 선택된 이미지 파일들과 대응 `annotations/{stem}.json`이 실제로 디스크에서
   삭제됐는지, 목록이 정상 갱신(reload)되는지, 선택하지 않은 이미지는 그대로 남는지.

5. 단일 선택(기존 동작) 회귀 없는지.

   크래시류가 현재 코드에서 재현되지 않음을 실측으로 재확인.
